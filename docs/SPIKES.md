# 技術検証の結果

`docs/DESIGN.md` §15 の検証項目を、`spikes/Snapwell.Spikes`（使い捨てのコンソール。製品には入れない）で確かめた結果。

- 実施日: 2026-10-17
- 環境: Windows 11（build 26200）、ARM64 の PC、ディスプレイは 60 Hz、拡大率 150%（DPI 144）
- 対象: 検証プログラムが自分で起動したメモ帳（Windows 11 の新しいメモ帳）。最後に閉じる
- OS の設定は読むだけで、変えていない
- 同じ検証を ARM64 ネイティブ（`win-arm64`）と、x64 のエミュレーション（`win-x64`）の両方で実行した

再実行:

```bash
dotnet build spikes/Snapwell.Spikes -c Release -r win-arm64 --self-contained
```

```bash
spikes/Snapwell.Spikes/bin/Release/net9.0-windows/win-arm64/Snapwell.Spikes.exe all
```

## 詳細

### 1. 代理描画（DwmRegisterThumbnail）

自分のプロセスで最前面のポップアップを作り、メモ帳のサムネイルを登録して、画面を取り込んだ輝度で中身が描かれているかを見た。

| 状態 | サムネイルの領域 | 元のウィンドウの領域 |
|---|---|---|
| サムネイルなし | 平均 239.6 / 標準偏差 9.7（背景だけ） | — |
| サムネイルあり、元はそのまま | 平均 41.8 / 14.1（メモ帳の中身） | 平均 45.5 / 34.9（メモ帳） |
| 元を `WS_EX_LAYERED` ＋ 透明度 0 | 平均 41.8 / 14.1（**描かれたまま**） | 平均 156.9 / 33.3（**後ろが見える＝隠れた**） |
| 元を仮想画面の外へ移動 | 平均 41.8 / 14.1（**描かれたまま**） | 平均 156.9 / 33.2（**隠れた**） |

- `DwmRegisterThumbnail` と `DwmUpdateThumbnailProperties` は `S_OK`。
- 他プロセスのウィンドウへの `SetWindowLongPtr(GWL_EXSTYLE)` と `SetLayeredWindowAttributes` は成功した。
- **注意**: レイヤードにする方法は、もともとレイヤードのウィンドウや、DirectComposition で描くアプリ（ブラウザ、Electron など）で壊れる可能性がある。**画面外へ移動する方法のほうが副作用が少ない**と考える（推測）。
- 未検証: 画面外に置いたあいだの中身の更新（動画などが止まるか）、ブラウザ・Office・Electron での挙動、移動の終わりに本物を戻すときのちらつき。

### 2. 角丸（DWMWA_WINDOW_CORNER_PREFERENCE）

`DONOTROUND`・`ROUND`・`ROUNDSMALL`・`DEFAULT` のどれも、他プロセスのウィンドウに対して `S_OK`。メモ帳はもともと角丸のため、見た目の変化は目視で確かめていない（MANUAL_TEST に回す）。

### 3. 標準スナップの設定（読むだけ）

| 値 | 結果 |
|---|---|
| `SPI_GETWINARRANGING` | 1（オン） |
| `HKCU\Control Panel\Desktop\WindowArrangementActive` | 1 |
| `HKCU\Control Panel\Desktop\DockMoving` | 1 |
| `HKCU\Control Panel\Desktop\SnapSizing` | 1 |
| `HKCU\...\Explorer\Advanced` の `SnapAssist`、`EnableSnapAssistFlyout`、`EnableSnapBar`、`SnapFill`、`JointResize`、`DITest` など | すべて値なし（既定） |

値が無いとき（既定）に、どの値を書けばフライアウトやスナップバーが止まるかは、書き込んで確かめる必要がある。OS の設定を変えるので、ユーザーの同意を得て手動で行う。

### 4. WM_NCHITTEST

| 位置 | 結果 | 時間（ARM64） |
|---|---|---|
| タイトルバーの中央 | `HTCAPTION` | 1.24 ms（初回） |
| タイトルバーの左寄り | `HTCAPTION` | 0.20 ms |
| クライアントの中央 | `HTCLIENT`（`WindowFromPoint` は子ウィンドウ。`GA_ROOT` で本体に戻る） | 0.07 ms |
| 閉じるボタン付近 | `HTCLOSE` | 0.08 ms |

長押しの判定に使える。`SendMessageTimeout` は低レベルフックのコールバックの中では呼ばず、別のスレッドで呼ぶ（CLAUDE.md の「フックのコールバックはすぐ返す」）。

### 5. SetWindowPos の速さ

| 操作 | ARM64 | x64 エミュレーション |
|---|---|---|
| 位置だけ（同期） | 平均 0.817 ms / 中央 0.434 / p95 2.278 / 最大 22.0 | 平均 0.412 ms / 中央 0.385 / p95 0.612 / 最大 1.24 |
| 位置だけ（`SWP_ASYNCWINDOWPOS`） | 平均 0.042 ms（呼んだ直後は位置が反映されていない） | 平均 0.023 ms |
| サイズの変更（同期） | 平均 27.3 ms / p95 37.1 / 最大 47.5 | 平均 24.4 ms / p95 31.8 / 最大 33.3 |
| `DwmFlush` の間隔 | 16.66 ms（60 Hz） | 16.67 ms（60 Hz） |

- 位置の移動は 1 フレーム（16.7 ms）に十分収まる。ARM64 の最大 22 ms は、初回の呼び出しによるもの（推測）。
- サイズの変更はアプリの再描画を待つため重い。毎フレームのサイズ変更は無理で、§5.4 のとおり着地時に 1 回だけにするか、代理描画を使う。
- `DwmFlush` で合成のタイミングに合わせられることを確認した。120 Hz 以上のディスプレイでは未確認。
