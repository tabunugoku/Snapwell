# Snapwell 基本設計書

版: 0.2（2026-10-17。製品名を Snapwell に決定）
状態: ドラフト（モックアップ作成前の基本設計）
関連資料: 競合調査レポート `reports/competitive-analysis.md`（ローカルのみ。Git に入れない）

---

## 1. 目的とポジション

製品名: **Snapwell**（Snap ＋ 磁石のポテンシャルの「井戸」。投げたウィンドウが区画に吸い込まれる挙動から）

業務PCで、ドック着脱やスリープを含む日常的な環境変化の中でも壊れず、GUIで設定できるウィンドウマネージャーを作る。物理挙動に基づく気持ちのよいスナップ（投げたウィンドウが角や区画に吸い込まれる操作感）を特徴とする。

競合調査で挙げた勝機との対応は次のとおり。

| 勝機 | 本設計での対応 |
|---|---|
| 業務利用を明確に許可するライセンス | ライセンス方針は別途決定（§13） |
| GUIで完結し、ホットキーを内蔵 | ホットキー、ランチャー、設定GUIを本体に内蔵する（§6, §9） |
| モニター構成の変化に強い | モニター構成ごとに状態を保存・復元する（§10.3） |
| Windows更新への耐性 | 非公開APIを使わず、DLLインジェクションもしない（§3.2） |

## 3. 全体アーキテクチャ

### 3.1 プロセス構成

```
┌────────────────────────── 本体プロセス（常駐・トレイ） ──────────────────────────┐
│                                                                              │
│  Input層            Core層                       Output層                     │
│  ┌──────────┐      ┌───────────────────┐       ┌──────────────────────┐      │
│  │ホットキー │─────▶│ Command Dispatcher │──────▶│ Window Mover          │      │
│  │LLキーボード│      │                   │       │ (SetWindowPos/        │      │
│  │フック     │      │ Layout Engine     │       │  DeferWindowPos)      │      │
│  ├──────────┤      │ (グリッド・間隔・   │       ├──────────────────────┤      │
│  │LLマウス   │─────▶│  整列)             │       │ Overlay Renderer      │      │
│  │フック     │      │                   │       │ (ランチャー・区画     │      │
│  ├──────────┤      │ Physics Engine    │       │  プレビュー・代理描画) │      │
│  │WinEvent   │─────▶│ (feel移植)         │       ├──────────────────────┤      │
│  │フック     │      │                   │       │ DWM Styler            │      │
│  └──────────┘      │ Window Registry   │       │ (角丸)                │      │
│                    │ Monitor Manager   │       └──────────────────────┘      │
│                    │ Settings Store    │                                     │
│                    └───────────────────┘                                     │
│                                                                              │
│  System Integration: 標準スナップ制御 / スタートアップ / 設定同期               │
└──────────────────────────────────────────────────────────────────────────────┘
          │ 名前付きパイプ（任意）
          ▼
   設定GUI（同じバイナリを別モードで起動、またはウィンドウを内包）
```

### 3.2 設計原則

1. **DLLインジェクションをしない。** フックは `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` と低レベルフック（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`）だけを使う。他プロセスへコードを注入しないため、対象プロセスのアーキテクチャ（x86、x64、ARM64、エミュレーション中のx64）と関係なく動き、x86版を作らない方針（R1）とも矛盾しない。
2. **非公開APIに依存しない。** 仮想デスクトップの非公開COM APIは使わない。ワークスペースが必要になった場合は自前で実装する。
3. **時間ではなく物理でアニメーションする。** 移動アニメーションは feel と同じく、質量・剛性・減衰から導く。継続時間やイージングを固定値で決めない（§5）。
4. **OS設定を変えたら必ず元に戻す。** 標準スナップの停止など、OS設定を変更する場合は変更前の値を保存し、終了時やクラッシュ後の再起動時に復元する（§8）。
5. **Per-Monitor DPI Aware v2 で動かす。** 座標はすべて物理ピクセルで扱う。

## 4. 技術スタック（推奨案）

| 項目 | 推奨 | 理由 |
|---|---|---|
| 言語・ランタイム | C# / .NET 9 以降、NativeAOT | x64・ARM64 のネイティブバイナリを1つのコードベースから出力できる。起動が速く、常駐時のメモリも小さい |
| Win32 相互運用 | CsWin32（ソースジェネレーター） | 型安全なP/Invokeを生成できる |
| 設定GUI | WinUI 3（Windows App SDK） | Windows 11標準の見た目。x64・ARM64対応 |
| オーバーレイ（ランチャー、区画プレビュー） | Win32 レイヤードウィンドウ ＋ DirectComposition / Direct2D | 透過・最前面・クリック透過・高リフレッシュレートでの描画に向く。WinUI 3は透過オーバーレイが苦手 |
| 配布 | MSIX（x64・ARM64のバンドル）＋ winget、ポータブル版のzip | 法人での配布（Intune）と個人での導入の両方に対応する |
| ビルド対象 | `win-x64`、`win-arm64` | **x86（`win-x86`）は作らない**。CIで両アーキテクチャをビルドし、ARM64の実機でテストする |

代替案: Rust（windows-rs）でコアを書き、GUIを別技術で作る構成。性能面では有利だが、GUIとの連携の手間が増えるため第一候補にはしない。

## 5. スナップ物理モデル（feel「03 · Card thrown to a corner」の移植）

### 5.1 元実装の要点（diip3sh/feel, MITライセンス）

| 要素 | feel での仕様 |
|---|---|
| モデル | 質量 m・剛性 k・減衰 c を持つ2次元の物体（`Body2D`）。ばねは両軸で同じ定数を使う（等方性）。壁は軸ごとに設定する |
| 言葉から数値へ | `Feel.words("airy, slightly magnetic")` が質量・固有振動数 f・減衰比 ζ を返す。k = m·(2πf)²、c = 2ζ·√(k·m) |
| ドラッグ | 座標を直接書き換えず、手（ポインタ）への「ハンドばね」の目標を更新する。重い物体ほどポインタから遅れる |
| リリース | 速度を保ったまま手を離す。惰性で止まる予測点は **x + v·m/c**。最終的な停止先は「惰性で止まる場所」から決め、ミリ秒の閾値は使わない |
| 停止点 | 4隅（時計回りに 0:左上、1:右上、2:右下、3:左下）。磁石場の強さの既定値は 0.6。吸い寄せの振動数は 0.6 + 0.5×強さ、吸着（クリック）の振動数は 3 + 4×強さ。吸着半径は 28px |
| 壁 | 可動範囲の端（0〜W、0〜H）を壁にし、行き過ぎを描画しない |
| 中断 | 移動中につかみ直すと、現在の位置と速度から続ける。速度をリセットせず、アニメーションをキューに積まない |
| フリック | 現在の角の対角（index+2）へ、指定した速さで弾く |
| 浮き上がり表現 | lift = min(1, 速さ/3000)。拡大率 1+0.05·lift、影のオフセット 4+16·lift、ぼかし 12+28·lift |
| 演算 | 全物体で1つのフレームループを共有し、全物体が静止したら止める。シミュレーションは240Hz |

### 5.2 ウィンドウへの適用

```
ユーザーがタイトルバーをドラッグ
  └─ EVENT_SYSTEM_MOVESIZESTART を検知 → 追跡を開始（ポインタの位置と時刻をリングバッファに記録）
ユーザーがマウスボタンを離す
  └─ EVENT_SYSTEM_MOVESIZEEND
       1. 直近 50〜80ms の軌跡から離した瞬間の速度 v を推定する
       2. 予測点 p = x + v·m/c を計算する
       3. p に最も近いスナップ先を選ぶ（候補: 四隅・半分・グリッド区画、§5.3）
       4. 速度が閾値未満で、予測点がスナップ先の吸着半径の外にある場合は何もしない
          （通常の移動として扱う）
       5. ばね・磁石場・壁のシミュレーションでウィンドウを停止点まで移動する
       6. 静止したら、最終的な矩形（サイズを含む）を確定する
```

- **壁:** 作業領域（タスクバーを除く領域）から余白（§6.3）を引いた範囲を壁にする。ウィンドウが画面外へはみ出して戻ってくる描画はしない。
- **マルチモニター:** 予測点が隣のモニターの作業領域に入る場合はそのモニターのスナップ先を候補に含め、モニター間の境界では壁を作らない。
- **中断:** 移動中にウィンドウを再びつかんだ場合（`EVENT_SYSTEM_MOVESIZESTART` またはマウスダウン）は、シミュレーションを即座に止め、制御をユーザーに返す。
- **操作感のプリセット:** 設定で feel の語彙（例: 「airy, slightly magnetic」「heavy」「snappy」）を選べるようにし、詳細設定では m・f・ζ・磁石の強さを直接調整できるようにする。
- **アクセシビリティ:** OSの「アニメーション効果」がオフ、またはアプリ設定でモーション削減が有効な場合は、停止点へ即座に移動する。

### 5.3 スナップ先（停止点）の候補

| 種類 | 内容 | 既定 |
|---|---|---|
| 四隅 | 現在のサイズのまま作業領域の四隅に置く（feel と同じ） | 有効 |
| 半分・四分割 | 左右・上下の半分と4分割 | 有効 |
| グリッド区画 | §6 のグリッドに揃えた位置。サイズは維持するか、投げた方向の区画に合わせるか選べる | 設定 |
| 最大化 | 上端への強いフリック | 設定 |

候補が多いと誤吸着が増えるため、候補点ごとの磁石の強さと吸着半径を持たせる。

### 5.4 移動の実装方式（要検証）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: 直接移動 | 毎フレーム `SetWindowPos(SWP_NOSIZE \| SWP_NOZORDER \| SWP_NOACTIVATE \| SWP_ASYNCWINDOWPOS)` を呼ぶ | 実装が単純で、どのウィンドウにも使える | 再描画の遅いアプリではカクつく。拡大・影などの浮き上がり表現はできない |
| B: 代理描画 | `DwmRegisterThumbnail` でウィンドウの縮小像を自前のオーバーレイに表示してアニメーションし、静止時に実際のウィンドウを1回で配置する | 高リフレッシュレートで滑らか。浮き上がり表現（拡大・影）を再現できる。サイズ変化も滑らかに見せられる | 移動中に元のウィンドウを隠す手段に制約がある（他プロセスのウィンドウはクローキングできない） |

**方針:** 既定はAとし、Bは技術検証（スパイク）で実現性を確かめてから「高品質モード」として追加する。サイズ変更はアニメーションせず、静止時に1回だけ適用する（再描画の負荷を避けるため）。

**検証の結果（`docs/SPIKES.md`）:** 位置の `SetWindowPos` は 1 回 1 ms 未満で、60 Hz で動かせる。サイズの変更は 1 回 24〜27 ms かかり、毎フレームは無理。Bは、他プロセスのウィンドウのサムネイルを描けること、元のウィンドウを画面外へ移動しても（またはレイヤード＋透明度 0 にしても）サムネイルが描かれ続けることを確認した。隠す方法は、副作用の少ない「画面外へ移動」を第一にする。

## 6. 画面分割（R2・R4）

### 6.1 グリッドモデル

- モニターごとに**分割案**（列数 N × 行数 M）を持つ。例: 8×8、12×6、6×4。既定は 8×8。
- 1区画を**基本単位**（unit）とする。ウィンドウのサイズは「横 a 区画 × 縦 b 区画」（a, b は正の整数）で表す。
- 区画の矩形は、間隔の設定（§6.3）を考慮して次の式で求める。

```
作業領域の幅 W、余白 e（画面端）、間隔 g（ウィンドウ同士）、列数 N のとき
  区画の幅 cw = (W − 2e − (N−1)·g) / N
  横 a 区画のウィンドウ幅 = a·cw + (a−1)·g
  列 i（0始まり）の左端 x = e + i·(cw + g)
（高さも同様に計算する）
```

- 端数は最後の区画に寄せ、合計が作業領域とずれないようにする。

### 6.2 一定比率でのサイズ変更（R4）

| 操作 | 内容 |
|---|---|
| 倍率指定 | 基本単位の ×1、×2、×3…（例: 8×8 なら 2×2 区画＝画面の 1/16） |
| 段階拡大・縮小 | 横・縦・両方向に1区画ずつ増減する。基準にする辺（左上固定、中心固定など）を選べる |
| プリセット比率 | 1/4、1/3、1/2、2/3、3/4 などを、分割案の区画数で表せる値として登録できる |
| 吸着 | 手動でリサイズしたあと、最も近い区画境界に揃える（任意） |

ウィンドウの最小・最大サイズの制約で区画に収まらない場合は、実際に適用されたサイズを読み直し、区画内で中央寄せ（または投げた方向の角に寄せ）して配置する。

### 6.3 間隔（R3）

| 設定 | 内容 | 既定 |
|---|---|---|
| ウィンドウ間隔 g | 隣り合うウィンドウの間のピクセル数 | 0（Windows標準と同じ隙間なし） |
| 画面端の余白 e | 作業領域の端とウィンドウの間のピクセル数 | g と連動（個別にも設定できる） |
| DPI スケーリング | g と e を論理ピクセルで指定し、モニターごとのDPIで換算する | 有効 |

**見えない枠の補正:** Windows 10/11 のウィンドウには、見た目の外側に約7pxの見えないリサイズ枠がある。`GetWindowRect` の値はこの枠を含むため、見た目の矩形は `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` で取得し、差分を補正して配置する。補正しないと間隔0でも隙間ができ、指定した間隔も正確にならない。

## 7. ウィンドウ整列（R3）

| 機能 | 内容 |
|---|---|
| グリッド自動整列 | 対象モニター上のウィンドウを、数に応じて行列に並べる |
| 列・行に整列 | 横一列、縦一列、メインと残りのスタック（マスター／スタック）型 |
| 隣接吸着 | ドラッグやキー操作で、隣のウィンドウの辺に g の間隔を空けて吸着する |
| 整列対象 | 現在のモニター／全モニター／選択したウィンドウ（ランチャーで複数選択） |
| 間隔の適用 | すべての整列で g と e を適用する。g=0 のときは隙間なしでぴったり並べる |

整列時の移動にも §5 の物理モデルを使う（設定でオフにできる）。複数のウィンドウは `BeginDeferWindowPos` でまとめて確定する。

## 8. Windows 標準機能との干渉防止（R6）

| 対象 | 制御方法（案） | 備考 |
|---|---|---|
| ドラッグでのスナップ（Aero Snap） | `SystemParametersInfo(SPI_SETWINARRANGING, FALSE)` | 設定アプリの「ウィンドウのスナップ」と同じ設定 |
| スナップレイアウト（最大化ボタンのフライアウト） | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced` の関連値 | 要検証。値の名前と効き方はWindowsビルドで変わる可能性がある |
| 画面上端のスナップバー（24H2以降） | 同上 | 要検証 |
| Win+矢印キー | 本ツールが有効な間だけ、低レベルキーボードフックで握りつぶして自前の操作に割り当てる | Explorerが予約しているため `RegisterHotKey` では登録できない |

**安全策:**

1. 変更前の値を設定ファイルとは別の状態ファイルに保存する。
2. 正常終了時と無効化時に元の値を復元する。
3. 起動時に状態ファイルが残っていれば、前回は異常終了したと判断して復元する。
4. 設定GUIに「標準の動作に戻す」ボタンを置き、手動でも復元できるようにする。
5. 初回有効化時に、変更するOS設定の一覧を表示して同意を得る。

## 9. 操作体系（R5）

### 9.1 ホットキー（既定案。すべて変更できる）

| 操作 | 既定キー |
|---|---|
| ランチャーを開く | Ctrl+Alt+Space |
| 左／右／上／下の半分 | Ctrl+Alt+←/→/↑/↓ |
| 四分割（左上・右上・左下・右下） | Ctrl+Alt+U / I / J / K |
| 1区画ずつ拡大・縮小 | Ctrl+Alt+Shift+矢印 |
| 区画単位で移動 | Ctrl+Alt+Win+矢印 |
| 現在のモニターを整列 | Ctrl+Alt+A |
| 隣のモニターへ投げる | Ctrl+Alt+PageUp / PageDown |
| 一時的に無効化 | Ctrl+Alt+Pause |

標準スナップを止めている間は、Win+矢印キーにも同じ操作を割り当てられる（§8）。ホットキーが競合した場合は、設定GUIで競合を検出して表示する。

### 9.2 ランチャー

- 対象ウィンドウがあるモニターの上に、半透明のオーバーレイとしてグリッドを表示する。
- **範囲選択:** マウスで区画をドラッグするか、キーボードで始点と終点の区画を指定して、ウィンドウの位置とサイズを決める（Divvyのような操作）。
- **プリセット:** よく使う配置（半分、1/3、整列など）をボタンで並べる。
- **フリック:** ランチャー上でウィンドウのサムネイルを投げると、§5 の物理モデルで配置される。
- Esc またはランチャー外のクリックで閉じる。

### 9.3 タイトルバーの長押し

```
WH_MOUSE_LL で左ボタンの押下を検知
  → WindowFromPoint → GetAncestor(GA_ROOT) で対象ウィンドウを特定
  → SendMessageTimeout(WM_NCHITTEST) が HTCAPTION を返すか確認
  → 長押しタイマーを開始（既定 450ms、変更可）
     ├─ 時間内に指定距離（既定 6px）以上動いた → キャンセル（通常のドラッグ、§5.2 のスナップへ）
     └─ 時間内に動かなかった → 標準の移動ループを取り消し、カーソル位置にランチャーを開く
```

- Chrome や Electron など独自のタイトルバーを持つアプリも、多くは `WM_NCHITTEST` に HTCAPTION を返すので判定できる。判定できないアプリ向けに「ウィンドウ上端 N px を長押し対象とする」補助ルールも用意する。
- 移動ループの取り消し方法（`ReleaseCapture` や Esc キーの送信など）はアプリごとに挙動が違う可能性があるため、要検証。

## 10. 対象ウィンドウの扱い（R11）

### 10.1 分類

| 分類 | 判定 | 位置の変更 | サイズの変更 |
|---|---|---|---|
| 通常のウィンドウ | 表示中、トップレベル、`WS_THICKFRAME` あり | ○ | ○ |
| サイズ固定のウィンドウ | `WS_THICKFRAME` なし、または最小＝最大サイズ | ○ | ×（区画内に中央寄せ、または投げた方向の角に寄せる） |
| ポップアップ・フライアウト（例: Claudeのタスクバーから開く小型チャット） | `WS_POPUP`、ツールウィンドウ、最前面など | ○ | × |
| UWP アプリ | `ApplicationFrameWindow` | ○（フレームウィンドウを移動する） | ○ |
| 管理者権限のウィンドウ | 本体より高い整合性レベル | 本体を管理者として起動したときだけ○ | 同左 |
| 除外 | デスクトップ、タスクバー、スタートメニューなどのシェル、クローキング中のウィンドウ、全画面の排他モード | × | × |

- フライアウトはフォーカスを失うと閉じるものが多いため、フォーカスを奪わずに（`SWP_NOACTIVATE`）移動する。ホットキー操作時は直前の前面ウィンドウを対象にする。
- アプリごとの除外ルールや強制ルール（プロセス名、ウィンドウクラス、タイトルの正規表現で指定）を設定できるようにする。
- 管理者権限のウィンドウ: UIPI（User Interface Privilege Isolation）により、通常権限からは操作できない。オプションで、タスクスケジューラ経由で管理者として自動起動できるようにする（§11）。

### 10.2 最小・最大サイズの扱い

他プロセスの `WM_GETMINMAXINFO` の値は直接取得できない。そのため、サイズを適用したあとに実際の矩形を読み直し、区画とずれていれば位置を補正する。

### 10.3 モニター構成の変化への対応

- モニター構成（各モニターのID、解像度、配置）の識別子をキーとして、ウィンドウの配置を保存する。
- `WM_DISPLAYCHANGE`、スリープ復帰（`WM_POWERBROADCAST`）、ドック着脱を検知したら、構成が落ち着くのを待ってから（デバウンス）、該当する構成の配置を復元する。
- 競合製品 komorebi で未解決になっている不具合（スリープ復帰やドック着脱で状態が失われる）を、本製品の重点テスト項目にする。

## 12. 設定（R8・R9）

### 12.1 保存形式

- JSON（スキーマのバージョンを持たせ、古い形式から自動で移行する）。保存先は `%APPDATA%\Snapwell\settings.json`。
- **ポータブル設定**（ホットキー、分割案、間隔、操作感、アプリごとのルール）と、**端末固有の状態**（モニター構成ごとの配置、標準スナップの退避値）を別ファイルに分ける。同期とエクスポートの対象はポータブル設定だけにする。

### 12.2 インポート・エクスポート

- 設定GUIからファイルに書き出し、読み込む。読み込み時には差分を表示し、全体を置き換えるか一部だけ取り込むかを選べるようにする。

### 12.3 クラウド同期（段階的に導入）

| 段階 | 方式 |
|---|---|
| 1 | ユーザーが選んだ同期フォルダー（OneDrive、Dropboxなど）に設定ファイルを置き、ファイルの変更を監視して取り込む。サーバーは不要 |
| 2 | アカウントを使った同期（GitHub Gist など）。必要性を見て判断する |

競合した場合は更新時刻で判断し、取り込む前に必ずバックアップを残す。

## 13. 角丸（R10）

| 方式 | 内容 | 評価 |
|---|---|---|
| DWM の角設定 | `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` で角丸、小さい角丸、角丸なしを指定する | Windows 11標準の仕組みで、影も保たれる。ただし**半径は固定**（約8px）。他プロセスのウィンドウに適用できるかは要検証 |
| ウィンドウ領域 | `SetWindowRgn` で角を切り取る | 半径は自由に決められるが、ギザギザになり、DWMの影が消える。アプリと干渉しやすいので非推奨 |
| オーバーレイで覆う | 角の部分を背景で覆うマスクを重ねる | 半径は自由だが、背景と合わせ続けるのが難しい |

**方針:** まずDWMの角設定を「角丸を強制する」機能として実装する（Windows 11の既定で角丸にならないウィンドウにも適用する）。macOS相当の大きな半径は、技術検証の結果を見て判断する。

## 14. 非機能要件

| 項目 | 目標 |
|---|---|
| 応答性 | ホットキーを押してから配置が終わるまで50ms以下（アニメーションなしの場合） |
| アニメーション | ディスプレイのリフレッシュレートに同期する（`DwmFlush` などで待つ）。演算は240Hzの固定ステップ |
| 常駐時の負荷 | アイドル時のCPU使用率ほぼ0%（フレームループは静止時に停止する）。メモリ50MB以下 |
| 堅牢性 | フックの処理が遅いとOSにフックを外されるため、フックのコールバックは即座に戻り、処理は別スレッドに渡す |
| 安全性 | OS設定を必ず復元できる（§8）。クラッシュ後の自動復旧 |
| 多言語 | 日本語・英語 |
| ライセンス | feel（MIT）のアルゴリズムを移植する場合は著作権表示を同梱する。本製品のライセンスは別途決定する（業務利用を明確に許可する方針） |

## 16. モックアップ作成の対象画面

次の工程で作るモックアップは以下を想定する。

1. **ランチャー**（グリッドのオーバーレイ、範囲選択、プリセット、ウィンドウのサムネイル）
2. **スナップ中の表示**（投げたウィンドウの軌跡、予測される停止先の区画のハイライト）
3. **設定GUI**（一般、分割と間隔、ホットキー、操作感（feel のプリセットとパラメーター）、アプリごとのルール、標準機能の制御、同期とインポート・エクスポート、外観（角丸））
4. **トレイメニュー**（有効・無効、プロファイルの切り替え、設定を開く）
5. **初回セットアップのウィザード**（標準スナップの停止への同意、ホットキーの確認、分割案の選択）
