## 1. 目的とポジション

製品名: **Snapwell**（Snap ＋ 磁石のポテンシャルの「井戸」。投げたウィンドウが区画に吸い込まれる挙動から）

業務PCで、ドック着脱やスリープを含む日常的な環境変化の中でも壊れず、GUIで設定できるウィンドウマネージャーを作る。物理挙動に基づく気持ちのよいスナップ（投げたウィンドウが角や区画に吸い込まれる操作感）を特徴とする。

競合調査で挙げた勝機との対応は次のとおり。

| 勝機 | 本設計での対応 |
|---|---|
| 業務利用を明確に許可するライセンス | ライセンス方針は別途決定（§13） |
| GUIで完結し、ホットキーを内蔵 | ホットキー、ランチャー、設定GUIを本体に内蔵する（§6, §9） |
| モニター構成の変化に強い | モニター構成ごとに状態を保存・復元する（§10.3） |
| Windows更新への耐性 | 非公開APIを使わず、DLLインジェクションもしない（§3.2） |

### 3.2 設計原則

1. **DLLインジェクションをしない。** フックは `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` と低レベルフック（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`）だけを使う。他プロセスへコードを注入しないため、対象プロセスのアーキテクチャ（x86、x64、ARM64、エミュレーション中のx64）と関係なく動き、x86版を作らない方針（R1）とも矛盾しない。
2. **非公開APIに依存しない。** 仮想デスクトップの非公開COM APIは使わない。ワークスペースが必要になった場合は自前で実装する。
3. **時間ではなく物理でアニメーションする。** 移動アニメーションは feel と同じく、質量・剛性・減衰から導く。継続時間やイージングを固定値で決めない（§5）。
4. **OS設定を変えたら必ず元に戻す。** 標準スナップの停止など、OS設定を変更する場合は変更前の値を保存し、終了時やクラッシュ後の再起動時に復元する（§8）。
5. **Per-Monitor DPI Aware v2 で動かす。** 座標はすべて物理ピクセルで扱う。

## 4. 技術スタック（推奨案）

| 項目 | 推奨 | 理由 |
|---|---|---|
| 言語・ランタイム | C# / .NET 9 以降、NativeAOT | x64・ARM64 のネイティブバイナリを1つのコードベースから出力できる。起動が速く、常駐時のメモリも小さい |
| Win32 相互運用 | CsWin32（ソースジェネレーター） | 型安全なP/Invokeを生成できる |
| 設定GUI | WinUI 3（Windows App SDK） | Windows 11標準の見た目。x64・ARM64対応 |
| オーバーレイ（ランチャー、区画プレビュー） | Win32 レイヤードウィンドウ ＋ DirectComposition / Direct2D | 透過・最前面・クリック透過・高リフレッシュレートでの描画に向く。WinUI 3は透過オーバーレイが苦手 |
| 配布 | MSIX（x64・ARM64のバンドル）＋ winget、ポータブル版のzip | 法人での配布（Intune）と個人での導入の両方に対応する |
| ビルド対象 | `win-x64`、`win-arm64` | **x86（`win-x86`）は作らない**。CIで両アーキテクチャをビルドし、ARM64の実機でテストする |

代替案: Rust（windows-rs）でコアを書き、GUIを別技術で作る構成。性能面では有利だが、GUIとの連携の手間が増えるため第一候補にはしない。

## 5. スナップ物理モデル（feel「03 · Card thrown to a corner」の移植）

### 5.1 元実装の要点（diip3sh/feel, MITライセンス）

| 要素 | feel での仕様 |
|---|---|
| モデル | 質量 m・剛性 k・減衰 c を持つ2次元の物体（`Body2D`）。ばねは両軸で同じ定数を使う（等方性）。壁は軸ごとに設定する |
| 言葉から数値へ | `Feel.words("airy, slightly magnetic")` が質量・固有振動数 f・減衰比 ζ を返す。k = m·(2πf)²、c = 2ζ·√(k·m) |
| ドラッグ | 座標を直接書き換えず、手（ポインタ）への「ハンドばね」の目標を更新する。重い物体ほどポインタから遅れる |
| リリース | 速度を保ったまま手を離す。惰性で止まる予測点は **x + v·m/c**。最終的な停止先は「惰性で止まる場所」から決め、ミリ秒の閾値は使わない |
| 停止点 | 4隅（時計回りに 0:左上、1:右上、2:右下、3:左下）。磁石場の強さは feel の語彙から決まる（magnetic = 1、clicky = 0.6、tactile = 0.5、「slightly」は 0.5 倍。語がなければ corner-card の既定の 0.6）。力は、最寄りの停止点への弱く遠くまで届くばね（吸い寄せの振動数 0.6 + 0.5×強さ）に、吸着半径の内側で滑らかに効く強いばね（吸着（クリック）の振動数 3 + 4×強さ）を足したもの。力 = −m(2π·reach)²·u − m(2π·click)²·u·smoothstep(1 − \|u\|/半径)。吸着半径（clickRadius）は corner-card では 28px（ライブラリの既定は 1 次元 18、平面 24） |
| 壁 | 可動範囲の端（0〜W、0〜H）を壁にし、行き過ぎを描画しない |
| 中断 | 移動中につかみ直すと、現在の位置と速度から続ける。速度をリセットせず、アニメーションをキューに積まない |
| フリック | 現在の角の対角（index+2）へ、指定した速さで弾く |
| 浮き上がり表現 | lift = min(1, 速さ/3000)。拡大率 1+0.05·lift、影のオフセット 4+16·lift、ぼかし 12+28·lift |
| 演算 | 全物体で1つのフレームループを共有し、全物体が静止したら止める。シミュレーションは240Hz |

### 5.2 ウィンドウへの適用

```
ユーザーがタイトルバーをドラッグ
  └─ EVENT_SYSTEM_MOVESIZESTART を検知 → 追跡を開始（ポインタの位置と時刻をリングバッファに記録）
ユーザーがマウスボタンを離す
  └─ EVENT_SYSTEM_MOVESIZEEND
       1. 直近 50〜80ms の軌跡から離した瞬間の速度 v を推定する
       2. 予測点 p = x + v·m/c を計算する
       3. p に最も近いスナップ先を選ぶ（候補: 四隅・半分・グリッド区画、§5.3）
       4. 速度が閾値未満で、予測点がスナップ先の吸着半径の外にある場合は何もしない
          （通常の移動として扱う）
       5. ばね・磁石場・壁のシミュレーションでウィンドウを停止点まで移動する
       6. 静止したら、最終的な矩形（サイズを含む）を確定する
```

- **壁:** 作業領域（タスクバーを除く領域）を壁にする。feel と同じく、壁は硬く減衰の効いたばね（剛性 m(2π·8)²、減衰比 0.9、押し込むときだけ減衰）で、止めるのではなく押し返す。そのため、非常に速い投げでは壁を数 px 越えてから戻る。停止点（余白 §6.3 を引いた位置）は壁の内側にある。
- **マルチモニター:** 予測点が隣のモニターの作業領域に入る場合はそのモニターのスナップ先を候補に含め、モニター間の境界では壁を作らない。
- **中断:** 移動中にウィンドウを再びつかんだ場合（`EVENT_SYSTEM_MOVESIZESTART` またはマウスダウン）は、シミュレーションを即座に止め、制御をユーザーに返す。
- **操作感のプリセット:** 設定で feel の語彙（例: 「airy, slightly magnetic」「heavy」「snappy」）を選べるようにし、詳細設定では m・f・ζ・磁石の強さを直接調整できるようにする。
- **磁石の強さと吸着半径（feel の磁石場の移植）:** `WindowBody` は feel の Body2D と同じく RK4・刻み 1/240 秒で動き、停止点を持つときは目標へのばねを使わず、磁石場の力 −m(2π·reach)²·u − m(2π·click)²·u·smoothstep(1 − |u|/半径)（u は最寄りの停止点からのずれ）で動く。減衰係数 c = 2ζ√(km) には語の固有振動数から導く k を使うが、力としては使わない。質量・固有振動数・減衰比は §5.1 の語彙（`FeelWords`）から決まり、設定画面のカードの語は airy, slightly magnetic ／ snappy, precise ／ heavy, settled ／ light, playful。磁石の強さは語から決まり（airy, slightly magnetic は 0.5、磁石の語がなければ 0.6）、設定で上書きできる（0〜2。feel の語は "super magnetic" で 1.8）。吸着半径の既定値は corner-card の 28px（物理ピクセルへは対象モニターの拡大率で換算）。手を離したあとの予測点は p + v·m/c。四隅モードは 4 つの角を停止点とした場の中を、離した速度のまま 6 秒を上限に動かして止まる角を選ぶ（feel の predict）。
- **区画の選び方（feel にない Snapwell 独自の部分と、場で決める部分）:** 区画モードでは、(1) 候補の絞り込みは Snapwell 独自のルール（モニター、最大化の条件、上下の行を決める 30%/70% の帯とカーソルの帯、隣の辺 24px）。最大化と隣の辺は候補が一つで、ルールの結果がそのまま選ばれる。(2) 残る左右の二候補は feel の磁石場で決める。窓の中心を、二つの区画の中心を停止点とする場の中で、離した速度のまま最大 6 秒動かし、止まった側を選ぶ。そのため、予測点（p+v·m/c）が反対側にあっても、手前の停止点に引き戻されれば元の側に止まる（feel の「勢いで決まる」）。(3) 選んだあとは、その区画の左上の一点を停止点とする場でウィンドウを動かす。feel に区画（矩形・サイズ）はないので、停止点は左上の一点にし、サイズは静止を確定したときに目標へ合わせる。
- **操作感の自由編集（カスタム）:** 4 つのプリセットは土台で、質量（0.15〜8）・固有振動数（0.4〜7 Hz）・減衰比（0.1〜1.6）・磁石の強さ（0〜2）は手で変えられる。範囲は feel の rig のスライダー（質量・振動数・減衰比）に合わせ、磁石の強さと吸着半径（8〜96）は Snapwell の設定。保存は「プリセット名（Feel）＋手で変えた値だけの上書き（`Mass`・`Frequency`・`DampingRatio`・`MagnetStrength`、未指定は null）」で、スキーマ版は 4 のまま（欠けた値は null で読むため、旧い版のファイルはプリセットのまま読める）。プリセットを選ぶと 4 つの上書きがすべて消え、値が表示上（小数 2 桁）プリセットと同じなら上書きにしない。上書きが一つでもあれば「カスタム」。取り込みの範囲外の値は、クランプではなくプリセットの値に戻す。**質量は、磁石場の力・壁・減衰がすべて質量に比例するため、吸着の動きを変えない**（feel でも、質量が効くのは手のばねと摩擦だけ）。k・c の表示にだけ効く。設定画面の「試す」は Core の `FeelTrial` で動かす。舞台を一つのモニターと見なして本体の `SnapResolver`（足切り・最大化の条件・左右の二候補を場で決める・四隅）に吸着先と停止点を決めさせ、動きは本体と同じ `WindowBody`。試す領域だけの規則は持たない。つかめるのはタイトルバー（高さ 30 px。実物より大きめ）だけで、判定は `FeelTrial.HitsTitleBar`（左と上の辺は含み、右と下は含まない。タッチとペンは四方へ 8 px 広げる）。
- **feel にない独自の扱い（そのほか）:** 隣の辺への吸着距離は論理 24px の固定値で、吸着半径とは別。速度 150px/s 未満は吸着しない（通常のドラッグと投げを分けるための、feel にない独自の足切り）。ホットキーの移動は feel の to(p)（目標へのばね）。物理の刻みは 1/240 秒、1 フレームの上限は feel のループと同じ 1/30 秒。設定画面のカードの曲線は feel の response()（閉形式）。
- **アクセシビリティ:** OSの「アニメーション効果」がオフ、またはアプリ設定でモーション削減が有効な場合は、停止点へ即座に移動する。

### 5.3 スナップ先（停止点）の候補

| 種類 | 内容 | 既定 |
|---|---|---|
| 四隅 | 現在のサイズのまま作業領域の四隅に置く（feel と同じ） | 有効 |
| 半分・四分割 | 左右・上下の半分と4分割 | 有効 |
| グリッド区画 | §6 のグリッドに揃えた位置。サイズは維持するか、投げた方向の区画に合わせるか選べる | 設定 |
| 最大化 | 上端への強いフリック | 設定 |

候補が多いと誤吸着が増えるため、候補点ごとの磁石の強さと吸着半径を持たせる。

区画モードでは、離した時点（プレビューでは現在）のカーソルが、対象モニターの作業領域の
上端に押し付けられていれば上の四分割、下端に押し付けられていれば下の四分割を選ぶ。
端の帯は、内側を論理 12px（対象モニターの拡大率で物理ピクセルへ換算）、外側を作業領域の高さの 10% までとし、
いずれも境界を含む。内側は端の近くのタイトルバーと押し付けたカーソルを分け、外側はタスクバー上のカーソルを拾う。
カーソルの X が作業領域の左端以上・右端未満のときだけ、この帯を使う。
外側の帯は、カーソルがほかのモニターの作業領域内にある場合は使わない。作業領域の包含は左端・上端を含み、
右端・下端を含まない。対象モニター自身の作業領域内にある内側の帯は従来どおり使う。
端に付いた背の高いウィンドウも、中心の高さに左右されず四分割にできるようにする。
帯の外や X の範囲外、ほかのモニター内の外側の帯、カーソル位置がない場合は、予測したウィンドウ中心による上下 30% の判定を使う。
左右と対象モニターは従来どおり予測中心で決め、上中央への強い投げによる最大化を四分割より優先する。
四隅モードはカーソル位置を使わない。

### 5.4 移動の実装方式（要検証）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: 直接移動 | 毎フレーム `SetWindowPos(SWP_NOSIZE \| SWP_NOZORDER \| SWP_NOACTIVATE \| SWP_ASYNCWINDOWPOS)` を呼ぶ | 実装が単純で、どのウィンドウにも使える | 再描画の遅いアプリではカクつく。拡大・影などの浮き上がり表現はできない |
| B: 代理描画 | `DwmRegisterThumbnail` でウィンドウの縮小像を自前のオーバーレイに表示してアニメーションし、静止時に実際のウィンドウを1回で配置する | 高リフレッシュレートで滑らか。浮き上がり表現（拡大・影）を再現できる。サイズ変化も滑らかに見せられる | 移動中に元のウィンドウを隠す手段に制約がある（他プロセスのウィンドウはクローキングできない） |

**方針:** 既定はAとし、Bは技術検証（スパイク）で実現性を確かめてから「高品質モード」として追加する。サイズ変更はアニメーションせず、静止時に1回だけ適用する（再描画の負荷を避けるため）。

**検証の結果（`docs/SPIKES.md`）:** 位置の `SetWindowPos` は 1 回 1 ms 未満で、60 Hz で動かせる。サイズの変更は 1 回 24〜27 ms かかり、毎フレームは無理。Bは、他プロセスのウィンドウのサムネイルを描けること、元のウィンドウを画面外へ移動しても（またはレイヤード＋透明度 0 にしても）サムネイルが描かれ続けることを確認した。隠す方法は、副作用の少ない「画面外へ移動」を第一にする。

## 6. 画面分割（R2・R4）

### 6.1 グリッドモデル

- モニターごとに**分割案**（列数 N × 行数 M）を持つ。例: 8×8、12×6、6×4。既定は 8×8。
- 1区画を**基本単位**（unit）とする。ウィンドウのサイズは「横 a 区画 × 縦 b 区画」（a, b は正の整数）で表す。
- 区画の矩形は、間隔の設定（§6.3）を考慮して次の式で求める。

```
作業領域の幅 W、余白 e（画面端）、間隔 g（ウィンドウ同士）、列数 N のとき
  区画の幅 cw = (W − 2e − (N−1)·g) / N
  横 a 区画のウィンドウ幅 = a·cw + (a−1)·g
  列 i（0始まり）の左端 x = e + i·(cw + g)
（高さも同様に計算する）
```

- 端数は 1 か所に寄せず、区画の幅の差が 1 px 以内になるよう分散させる。列 i の左端は `左 + e + floor(i·(W − 2e + g) / N)` とし、最後の区画の右端がちょうど `右 − e` になる（実装は `Snapwell.Core.Layout.GridLayout`）。

### 6.2 一定比率でのサイズ変更（R4）

| 操作 | 内容 |
|---|---|
| 倍率指定 | 基本単位の ×1、×2、×3…（例: 8×8 なら 2×2 区画＝画面の 1/16） |
| 段階拡大・縮小 | 横・縦・両方向に 1〜4 区画ずつ増減する（設定の `ResizeStep`）。固定する位置は左上・中心・近い辺（作業領域の端に近いほうの辺。軸ごとに決める）から選べる（`ResizeAnchor`） |
| プリセット比率 | 1/4、1/3、1/2、2/3、3/4 などを、分割案の区画数で表せる値として登録できる |
| 吸着 | 手動でリサイズしたあと、最も近い区画境界に揃える（任意） |

ウィンドウの最小・最大サイズの制約で区画に収まらない場合は、実際に適用されたサイズを読み直し、区画内で中央寄せ（または投げた方向の角に寄せ）して配置する。

### 6.3 間隔（R3）

| 設定 | 内容 | 既定 |
|---|---|---|
| ウィンドウ間隔 g | 隣り合うウィンドウの間のピクセル数 | 0（Windows標準と同じ隙間なし） |
| 画面端の余白 e | 作業領域の端とウィンドウの間のピクセル数 | g と連動（個別にも設定できる） |
| DPI スケーリング | g と e を論理ピクセルで指定し、モニターごとのDPIで換算する | 有効 |

**見えない枠の補正:** Windows 10/11 のウィンドウには、見た目の外側に約7pxの見えないリサイズ枠がある。`GetWindowRect` の値はこの枠を含むため、見た目の矩形は `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` で取得し、差分を補正して配置する。補正しないと間隔0でも隙間ができ、指定した間隔も正確にならない。

## 7. ウィンドウ整列（R3）

| 機能 | 内容 |
|---|---|
| グリッド自動整列 | 対象モニター上のウィンドウを、数に応じて行列に並べる |
| 列・行に整列 | 横一列、縦一列、メインと残りのスタック（マスター／スタック）型 |
| 隣接吸着 | ドラッグを離した予測位置が、隣のウィンドウの辺から論理 24 px 以内なら、その辺に g の間隔を空けて吸着する（サイズは変えない）。吸着方式が区画のときだけで、最大化の投げと、カーソルが画面の上端・下端の帯にあるときは区画を優先する。ドラッグ開始時に隣のウィンドウを一度だけ取り、プレビューと離したときで同じ一覧を使う。キー操作は前面のウィンドウを上下左右の最も近い隣の辺へ寄せる（下記） |
| 整列対象 | 現在のモニター／全モニター／選択したウィンドウ（ランチャーの展開した一覧でクリックまたは数字キーにより最大 9 件を複数選択し、選んだウィンドウだけをランチャーのあるモニターへ整列する） |
| 間隔の適用 | すべての整列で g と e を適用する。g=0 のときは隙間なしでぴったり並べる |

キー操作の隣接吸着は、吸着方式によらず、指定方向の軸だけ位置を変え、直交する軸と幅・高さを保つ。
候補は、直交軸で正の長さだけ重なり、指定方向側に辺がある隣のウィンドウとする。
右方向なら `neighbor.X >= current.Right` の辺から g を引き、現在の幅を引いた X へ寄せる
（左・上・下も同様）。作業領域と交わらない隣や、方向側に辺がない重なった隣は無視する。
現在と同じ位置になる候補と、辺に寄せると作業領域の余白 e を侵す候補を除き、移動量が最小のものを選ぶ。
候補がなければ、その方向の作業領域の端から e 空けた位置へ寄せる。既に同じ位置なら何もしない。
移動軸の座標は余白内へ Clamp し、ウィンドウが大きすぎる場合はその軸の開始側の余白へ揃える。
g と e は対象モニターの DPI で物理ピクセルに換算する。隣の一覧は App の
`NeighborWindowSource.Snapshot(handle)` から Core の `AdjacentSnapPlanner` へ渡す。
サイズ固定も位置だけ動かし、最大化中は通常状態に復元してから計画する。移動には §5 の物理モデルを使う。
操作は `WindowCommand` の既存の整数値を保って末尾に追加する。既定のキーは Ctrl+Alt+Shift+J・L・I・K（左・右・上・下。Win は付けない）。
設定のスキーマ版は 5 とし、版 5 未満で操作が未割り当てかつ同じキーが未使用の場合だけ既定値を補う。

整列時の移動にも §5 の物理モデルを使う（設定でオフにできる）。複数のウィンドウは `BeginDeferWindowPos` でまとめて確定する。

- 物理演算は変更せず、フレームごとに計画した位置（Position）を `BeginDeferWindowPos` → `DeferWindowPos` → `EndDeferWindowPos` で一括確定する。対象が 2 つ以上のときだけバッチにし、1 つなら従来の `MoveVisual` を使う。`IWindowMover.ApplyBatch` と `IWindowPositionApi.ApplyBatch` の `positionOnly` が true のときは `SWP_NOSIZE` を付け、サイズ・Z 順序・フォーカスを変えない。
- 静止した対象の最終サイズ（Bounds）は従来どおり個別に適用し、実矩形を読み直す。Position と Bounds が混在するときは元の順序を保ち、Bounds の前後で連続する Position のバッチを区切る。
- モーション削減時は最終 Bounds を 2 つ以上まとめてサイズつきバッチ（`positionOnly=false`）で適用する。その後は対象ごとに実矩形を読み直し、最小・最大サイズの制約などで Walls をはみ出した場合だけ `MoveVisual` で寄せる。Walls より大きい寸法は Walls の左端・上端に合わせる。1 つの場合とバッチ失敗時は従来の個別経路を使う。
- バッチを組み立てる間はエンジンのロックを持ち、各対象のエントリーとバージョン（`IsCurrent`）を確認して、取り消し・差し替え済みの対象を外す。同じハンドルを 1 フレームに重複させない。外部 API はロックの外で呼び、返らない場合も取り消し・新規要求・終了を妨げない。確認直後から外部呼び出しまでの間の取り消しは、個別経路と同じく進行中の 1 回を止められない。終了後は新たな適用・読み直し・補正を開始しない。
- バッチが false または例外で失敗したフレームは、対象全員を元の順序で個別適用へ戻して再試行する。その際も対象ごとに `IsCurrent` を確認し、失敗した対象のエントリーだけを外す。サイズ適用はバッチからの再試行を除いて最終の 1 回とし、新しい要求のエントリーを古い結果で消さない。
- `WindowMover` は最大化した対象を既存の `TryPrepare` で復元し、通常状態の見えない枠を取り直して補正する。調査・復元が失敗または例外になった対象はバッチから除き、そのハンドル一覧を呼び出し側へ返す。残りの対象のバッチは続行し、全対象を除いた場合はネイティブ API を呼ばない。サイズつきのフラグと枠補正の扱いは従来どおりとする。

ホットキー操作では、前面のウィンドウがある現在のモニターを対象に、通常とサイズ固定のウィンドウを 4 つの方式（グリッド・横一列・縦一列・メインとスタック）で整列する。グリッドは `ceil(sqrt(count))` 列×`ceil(count/列数)` 行（縦長の作業領域では列と行を入れ替え、最後の行は残りのウィンドウで行幅を等分）、メインとスタックは前面のウィンドウを左半分・残りを右半分に縦等分する。並べる順は見た目の矩形の中心座標で決める（横一列は X、縦一列は Y、グリッドは Y の次に X、メインとスタックは前面のウィンドウを先頭にして残りを Y の小さい順）。既定のキーはグリッド整列が Ctrl+Alt+A（スキーマ版 3 で移行）、横一列・縦一列・メインとスタックが Ctrl+Alt+Shift+H・V・M、全モニターのグリッド整列が Ctrl+Alt+Shift+A（スキーマ版 4 で移行。同じキーが割り当て済みなら足さない）。全モニターの整列は、各モニターに属するウィンドウをモニターごとにグリッドで並べ、前面のウィンドウを先頭にしない。トレイメニューの「現在のモニターを整列」は、前面が Snapwell 自身になるため、カーソルがあるモニターをグリッドで整列する。ランチャーでの複数選択と選択対象の整列は §9.2 の操作を使う。

## 8. Windows 標準機能との干渉防止（R6）

| 対象 | 制御方法（案） | 備考 |
|---|---|---|
| ドラッグでのスナップ（Aero Snap） | `SystemParametersInfo(SPI_SETWINARRANGING, FALSE)` | Windows の設定アプリの「ウィンドウのスナップ」と同じ設定 |
| スナップレイアウト（最大化ボタンのフライアウト） | 上の `SPI_SETWINARRANGING` で一緒に止まる | ARM64 の Windows 11 26300 で、セッション限りの停止だけで消えることを確認した。レジストリは触らない。個別に止める `EnableSnapAssistFlyout` は、書き換えても Explorer の再起動まで反映されず、公開 API の通知（`WM_SETTINGCHANGE`）も効かなかったため使わない |
| 画面上端のスナップバー（24H2以降） | 同上 | 同上（`EnableSnapBar` も同じ理由で使わない）。ドラッグ中の灰色の枠も一緒に止まる |
| Win+矢印キー | 端末の `ReplaceWinArrow` がオンで本体が有効な間だけ、低レベルキーボードフックで標準の操作を握りつぶす | Win だけを修飾にした ←・→・↑・↓ を左・右・上・下の半分にする固定の 4 割り当て。利用者の同じキーの組を優先する。Win を押している間（最初の握りつぶした矢印）に、別スレッドの `SendInput` で `VK_NONAME` の押下と解放を 1 回送り、スタートメニューの起動を抑える |
| 他プロセスのウィンドウの角 | `DWMWA_WINDOW_CORNER_PREFERENCE`（§13） | 変更前の値を `corners.json` に退避し、既定へ戻したとき・無効化・終了・異常終了後の起動で復元する |

Win+矢印は XAML の KeyDown へ届かず取り込めないため、標準機能ページの一つのスイッチで固定の
4 割り当てを追加する。既定はオフで、`device.json` に即時保存し、監視で再起動なしに反映する。
OS の設定は変えないので同意ダイアログは出さない。標準の最大化・最小化は置き換え中には使えない。
一時停止中は再開のキーだけ、ランチャー表示中は従来の専用割り当てだけを残す。
ダミー入力は、Win を含む Suppress=true の割り当ての最初のキー押下を握りつぶした時点で専用スレッドへ要求し、
Win を押している間に一度だけ送る。左右の Win を両方離したら記録を消し、解放時には送らない。
専用スレッドの合図は一件分だけとし、イベントの配送キューは使わない。送信失敗は無視し、停止・破棄も送信完了を待たない。
フック内の同期送信は他の低レベルフックの遅れでタイムアウトし、OS にフックを外されうるため使わない。
Win の解放を握りつぶして送り直す方式も、直後のキーが Win+キーとして読まれたり、送信役が止まると Win が押されたままに見えたりするため使わない。
Win の解放自体は OS に通し、`LLKHF_INJECTED` の入力は自分のフックで判定しない。
Win 単独や未割り当ての Win+D、キー取り込み中、割り当てのない一時停止中には送らない。
端末状態のスキーマは版 3 とし、版 2 以前の `ReplaceWinArrow` は false に移行する。

**安全策:**

1. 変更前の値を設定ファイルとは別の状態ファイルに保存する。
2. 正常終了時と無効化時に元の値を復元する。
3. 起動時に状態ファイルが残っていれば、前回は異常終了したと判断して復元する。
4. 設定GUIに「標準の動作に戻す」ボタンを置き、手動でも復元できるようにする。端末状態の最新値に対し、`DisableStandardSnap` と `ReplaceWinArrow` を一度の保存で false にし、保存済みの同意とほかの項目は保持する。Win+矢印の置き換えだけがオンのときも復元できる。ボタンの右に退避値の説明は表示しない。
5. 初回有効化時に、変更するOS設定の一覧を表示して同意を得る。

初回起動では、本体が設定画面を `--setup` で開き、「ようこそ → 標準機能 → ホットキー → 分割案」の
4 手順を案内する。本体は完了を待たずに常駐するが、標準スナップの停止は手順 2 の「次へ」で
`DisableStandardSnap`・`ReplaceWinArrow`・`StandardSnapConsentGiven` を同じ値で保存した後だけ行う（Win+矢印の置き換えも、
同意と同時にオンになる）。チェックを外しても先へ進める。
端末状態の保存を監視し、同意の変更を起動中の本体にも反映する。無効化・終了・異常終了後の復元は従来どおり行う。
設定画面の「一般」ページの「Snapwell を有効にする」は、保存ボタンを待たず操作の時点で端末状態の `Enabled` を書く（トレイのトグルと同じ即時の動作。起動中の本体は上の監視で追従する）。本体が起動していなくても書け、読み書きに失敗したときは InfoBar を出してスイッチを戻す。ページを開くたびに読み直し、開いたままの間のトレイでの切り替えには追従しない。

ウィザードは通常の設定画面と別の単一インスタンスで、再起動要求では同じユーザーのウィザードを前面に出す。
途中で閉じる（Esc を含む）と未完了のままにし、次の本体起動で再表示する。スキップは設けない。
ホットキーは §9.1 の設定内の重複検出と Windows の一時登録の可否で確認する。重複があっても進められ、
未割り当ての操作はその状態を表示する。他アプリの低レベルフックによる横取りまでは判定できない。
最後に §6 の 8×8・12×6・6×4 と間隔 0〜24 px を選び、画面端の余白も同じ間隔にする。
既存ストアで最新の設定を読み直し、ほかの項目を保ったまま `settings.json` を保存してから
端末状態の `SetupCompleted` を true にする。保存失敗や未来の版で読み取り専用の場合は完了にせずエラーを示す。
端末状態のスキーマは版 3 とし、版 1（版なしを含む）は完了済みに移行する。
端末状態がなくても既存の設定ファイルがある場合は完了済みとする。版 2 の明示的な未完了状態は再表示する。

## 9. 操作体系（R5）

### 9.1 ホットキー（既定案。すべて変更できる）

| 操作 | 既定キー |
|---|---|
| ランチャーを開く | Ctrl+Alt+Space |
| 左／右／上／下の半分 | Ctrl+Alt+←/→/↑/↓ |
| 四分割（左上・右上・左下・右下） | Ctrl+Alt+U / I / J / K |
| 中央に配置 | Ctrl+Alt+C |
| 中央に配置（サイズ維持） | Ctrl+Alt+Shift+C |
| 1区画ずつ拡大・縮小 | Ctrl+Alt+Shift+矢印 |
| 区画単位で移動 | Ctrl+Alt+Win+矢印 |
| 左／右／上／下の隣へ寄せる | Ctrl+Alt+Shift+J / L / I / K |
| 現在のモニターを整列 | Ctrl+Alt+A |
| 横一列／縦一列／メインとスタックで整列 | Ctrl+Alt+Shift+H / V / M |
| 全モニターを整列 | Ctrl+Alt+Shift+A |
| 隣のモニターへ投げる | Ctrl+Alt+PageUp / PageDown |
| 一時停止・再開 | Ctrl+Alt+Pause |

Win+矢印の固定の半分操作は、標準スナップの停止とは独立して端末ごとに選べる（§8）。
設定画面のキーの欄をクリックして新しいキーを押すと割り当てを変えられる。Ctrl・Alt・Shift・Win のどれかを含める。
Esc でやめ、修飾キーなしの Backspace・Delete で割り当てを外す。各操作またはすべてを既定に戻せ、変更は「保存」で確定する。
同じキーがあると「重複」を表示し、「入れ替える」「重複のまま割り当てる」「やめる」を選ぶ。
ページを開いたときと割り当ての変更後に、RegisterHotKey の一時登録・即時解除でほかのアプリと OS の使用を調べる。
新しいキーが使用中なら確認してから割り当て、一覧には「ほかのアプリが使用中」と表示する。
低レベルフックで受けるほかのアプリのキーは検出できない。Windows の予約キーは割り当てても届かない場合がある。
Win キーを含む割り当てを握りつぶした後のスタートメニューは、§8 のダミー入力で抑える。
Win+L などシェルが先に処理する予約キーまで置き換えることは保証しない。
広げる・縮める 4 操作の名前は、「分割と間隔」の「固定する位置」と区画数に合わせて変わる。

### 9.2 ランチャー

ランチャーはホットキー（既定 Ctrl+Alt+Space）とトレイのメニューから開く。
タイトルバーの長押しは、クリックやタイトルバー以外の操作で誤作動を招きやすいため廃止した。

- 対象ウィンドウがあるモニターの上に、半透明のオーバーレイとしてグリッドを表示する。
- **範囲選択:** マウスで区画をドラッグするか、キーボードで始点と終点の区画を指定して、ウィンドウの位置とサイズを決める（Divvyのような操作）。
- **プリセット:** 上半分・下半分・左半分・右半分、左上・右上・左下・右下の 1/4、左・右の 1/3、左・右の 2/3、中央 1/3、中央（サイズ変更）、中央（サイズ維持）、最大化の 16 個。設定の「ランチャー」（ナビゲーションでは「外観」の前）でグループ別のチェック、すべて選ぶ・すべて外す・既定に戻すを使い、件数とプレビューを確認できる。
- **表示するプリセットの保存:** `LauncherPresets` にモックアップの安定した ID を保存する。順序は `top, bottom, left, right, tl, tr, bl, br, l3, r3, l23, r23, c3, center, centerKeep, max` に固定し、未知・重複は除く。既定は `left, right, tl, l3, r23, c3, center, max` の 8 個。空の一覧も有効で、「表示するプリセットがありません（設定の「ランチャー」で選べます）」を行の高さを保って表示する。設定の再読込後、次回のランチャー表示へ反映する。
- **プリセットの操作:** 区画の整数倍で作れない比率は無効。サイズ維持の中央だけは常に有効で、アイコンは破線の枠とする。押すと対象ウィンドウの見た目の幅・高さを保ち、現在の作業領域の中央へ既存の物理モデルの配置経路で移して閉じる。それ以外は区画の選択へ反映し、Enter で配置する。
- **ウィンドウ一覧:** 通常・サイズ固定のトップレベルウィンドウを全モニターから表示する。「ウィンドウを選んで整列」は開くたびに折りたたみ、見出しと「未選択」または「選択 n / 9」の一行を表示する。見出しのクリックで展開し、行のクリックで最大 9 件を選ぶ。10 件目は無視して状態メッセージで知らせる。一ページは 9 件で、「前へ」「次へ」でページを送り、ページ内の長い一覧はスクロールバーで動かす。行には固定幅の番号・チェック・省略したタイトル・選択順の先頭の「メイン」（青の輪と点）／後続の「スタック」（灰色の輪）を、ラジオ形式の図形アイコンつきで表示する。アイコンは文字ではなく図形で描く。通常クリックによる配置対象の切替は廃止する。区画のドラッグ・矢印・Shift+矢印・Enter による配置は従来どおり。
- **選択したウィンドウの整列:** 4 ボタン（グリッド・横一列・縦一列・メインとスタック）、または Alt+1〜4 で実行して閉じる。未選択のボタンは無効で、方式キーでも何もしない。選んだ対象だけを、別モニターの対象も含めてランチャーの作業領域へ並べる。メインとスタックのメインは最初に選んだ有効なウィンドウ。間隔と余白は整列先の DPI で換算する。移動は既存の配置経路へ渡し、物理モデル・モーション削減・バッチ確定を共用する。アイコンはモックアップの 44 × 28 の座標を使い、ラベルはボタンの全幅と描画フォントの実測幅を基準に中央へ置く。
- **一覧のキー操作:** 展開中の修飾キーなしの 1〜9 は、ページ内の n 番目の選択を切り替える。Alt+1〜4 は整列する。折りたたみ中の数字と Alt+数字は何もしない。Ctrl+1〜4、Ctrl+Space、Tab／Shift+Tab による一覧操作は廃止する。Ctrl・Shift・Win の同時押しでは数字選択を行わず、長押しの繰り返しも無効。既存のキー割り当てと競合するときは一時キーだけを外す。
- 閉じる・配置対象を変える・整列を実行するたびに選択を解除する。閉じた・最小化・クローク・自プロセス・所有されたダイアログなどは整列時に再調査して除外し、除外件数を呼び出し側へ返す。選択した全対象が無効でもモニター全体の整列には切り替えない。表示先のモニターがなくなったり作業領域・DPI が変わったりした場合は閉じ、古い座標で整列しない。
- **フリック:** ランチャー上でウィンドウのサムネイルを投げると、§5 の物理モデルで配置される。
- Esc またはランチャー外のクリックで閉じる。

## 10. 対象ウィンドウの扱い（R11）

### 10.1 分類

| 分類 | 判定 | 位置の変更 | サイズの変更 |
|---|---|---|---|
| 通常のウィンドウ | 表示中、トップレベル、`WS_THICKFRAME` あり | ○ | ○ |
| サイズ固定のウィンドウ | `WS_THICKFRAME` なし、または最小＝最大サイズ | ○ | ×（区画内に中央寄せ、または投げた方向の角に寄せる） |
| ポップアップ・フライアウト（例: Claudeのタスクバーから開く小型チャット） | `WS_POPUP`、ツールウィンドウ、最前面など。操作の対象はホットキーとドラッグだけで、整列・隣接吸着・ランチャーの一覧には含めない。設定 MovePopupWindows（既定オン）で対象から外せる | ○ | × |
| UWP アプリ | `ApplicationFrameWindow` | ○（フレームウィンドウを移動する） | ○ |
| 管理者権限のウィンドウ | 本体より高い整合性レベル | 本体を管理者として起動したときだけ○ | 同左 |
| 除外 | デスクトップ、タスクバー、スタート メニューなどのシェル、クローキング中のウィンドウ、全画面の排他モード | × | × |

- フライアウトはフォーカスを失うと閉じるものが多いため、フォーカスを奪わずに（`SWP_NOACTIVATE`）移動する。ホットキー操作時は直前の前面ウィンドウを対象にする。
- アプリごとの除外ルールや強制ルール（プロセス名、ウィンドウクラス、タイトルの正規表現で指定）を設定できるようにする（§10.4）。
- 管理者権限のウィンドウ: UIPI（User Interface Privilege Isolation）により、通常権限からは操作できない。オプションで、タスクスケジューラ経由で管理者として自動起動できるようにする（§11）。

### 10.2 最小・最大サイズの扱い

他プロセスの `WM_GETMINMAXINFO` の値は直接取得できない。そのため、サイズを適用したあとに実際の矩形を読み直し、区画とずれていれば位置を補正する。

### 10.3 モニター構成の変化への対応

- モニター構成（各モニターのID、解像度、配置）の識別子をキーとして、ウィンドウの配置を保存する。
- `WM_DISPLAYCHANGE`、スリープ復帰（`WM_POWERBROADCAST`）、ドック着脱を検知したら、構成が落ち着くのを待ってから（デバウンス）、該当する構成の配置を復元する。
- 競合製品 komorebi で未解決になっている不具合（スリープ復帰やドック着脱で状態が失われる）を、本製品の重点テスト項目にする。


### 10.4 アプリごとのルール

特定のアプリのウィンドウを、Snapwell の対象から外したり、動かし方やウィンドウの角（§13）を変えたりする。ポップアップやフライアウト、ゲームのランチャー、ピクチャー イン ピクチャーなど、分類（§10.1）や全体設定だけでは扱いを決められないウィンドウのための例外である。例: 全体設定で「角丸を強制する」にすると、フレームなしの浮かぶウィンドウ（Claude のチャットバーなど）に四角い枠が出ることを実機で確認した。そのウィンドウだけ角を触らないようにできる。

**ルールの形**

| 項目 | 内容 |
|---|---|
| 有効 | オフにしても、ルールは残る |
| プロセス名 | 実行ファイル名（例: `chrome.exe`）。完全一致、大文字小文字は区別しない |
| ウィンドウ クラス | 完全一致、大文字小文字は区別しない |
| タイトル | 正規表現、大文字小文字は区別しない。部分一致（全体に合わせるときは `^` と `$` を書く） |
| 配置の扱い | 「全体設定に従う」（既定）「対象外」「位置だけ」「強制的に対象」 |
| 角 | 「全体設定に従う」（既定）「Windows の既定（Snapwell は変更しない）」「角丸を強制する」「小さい角丸」「角丸なし」 |

- 条件は 3 つのうち 1 つ以上を指定し、指定したものすべてに一致したときに適用する（AND）。指定のない条件は見ない。条件が 1 つもないルール、および配置の扱いも角も「全体設定に従う」のルール（何も決めないルール）は保存しない。
- 「OR」にしたいときは、ルールを複数並べる。
- ルールは 200 件まで。

**配置の扱い**

| 扱い | 位置の変更 | サイズの変更 | 用途 |
|---|---|---|---|
| 対象外 | × | × | 配置の操作の対象にしない。ゲームのランチャー、独自の配置を持つアプリなど |
| 位置だけ | ○ | ×（区画内に中央寄せ、または投げた方向の角に寄せる。サイズ固定のウィンドウと同じ） | ピクチャー イン ピクチャーなど、大きさを変えたくないウィンドウ。全体設定 MoveFixedSizeWindows がオフでも動かす |
| 強制的に対象 | ○ | ○ | ポップアップやサイズ固定と判定されても、通常のウィンドウとして扱う。整列・隣接吸着・ランチャーの一覧にも含める |

- 「対象外」は移動・サイズ変更・吸着に関するすべての操作（ホットキー、ドラッグでの吸着、整列、隣接吸着、ランチャーの一覧、四隅へ投げる操作、選択したウィンドウの整列）から外す。操作ごとに選ぶ機能は作らない。ウィンドウの角には影響しない（角は下の「ウィンドウの角」で別に決める）。
- 「強制的に対象」でも、もとの分類がポップアップのウィンドウは、フォーカスを奪わない移動（`SWP_NOACTIVATE`、§10.1）を保つ。サイズが実際には変わらなかったときは、§10.2 の位置の補正に従う。

**判定の順序**

1. **常に対象外（ルールで変えられない）**: 非表示、クローク中、最小化、自プロセス、子ウィンドウ、デスクトップ・タスクバー・スタート メニューなどのシェル、通知領域の隠れたアイコンの一覧（§10.1 の「除外」）。「強制的に対象」でも対象にならない。
2. ルールを一覧の上から順に調べる。**配置の扱いと角は別々に**、そのプロパティが「全体設定に従う」以外になっている**最初の一致ルール**を採る（例: 上のルールが角だけを決め、下のルールが配置だけを決めていれば、両方が効く）。無効のルールは飛ばす。順序は設定画面で入れ替えられる。
3. 一致するルールがなければ（そのプロパティを決めるルールがなければ）、配置は §10.1 の分類と MoveFixedSizeWindows・MovePopupWindows の全体設定に、角は全体設定の CornerPreference（§13）に従う。

判定は 1 つの窓口（Platform の `WindowTargetResolver`。分類とルールの結果を返す）に集める。いま `WindowClassifier.Classify` を直接呼んでいる箇所（ホットキー、ドラッグ、隣接吸着、整列、ランチャー、四隅、前面ウィンドウの追跡）はすべてこの窓口を通し、操作によって扱いが食い違わないようにする。

**ウィンドウの角**

- 角の指定は、DWM の角の設定（§13）をそのウィンドウだけ上書きする。「Windows の既定」は、全体設定が「角丸を強制する」でも、そのウィンドウには何も変えない（すでに変えていれば元に戻す）。
- 角の指定があるウィンドウは、分類にかかわらず（常に対象外のものと最大化中のものを除いて）適用する。分類が「ポップアップ」でも、利用者が明示した指定を優先する。
- 角はウィンドウが表示されたとき、およびルール・全体設定を変えたときに決め直す。ルールの追加・変更・削除は、開いているウィンドウにも反映し、ルールから外れたウィンドウは、全体設定の値か元の値に戻す（変更前の値は既存の退避、`corners.json` を使う）。
- タイトルの条件で角を決めるウィンドウは、タイトルが後から変わっても決め直さない（実機未確認。名前の変更の通知を購読すれば追従できるが、この版では作らない）。タイトルが変わるアプリには、プロセス名かクラスで指定する。

**値の取り方と注意**

- プロセス名は `QueryFullProcessImageNameW`（`PROCESS_QUERY_LIMITED_INFORMATION`。公開 API）で取る。ルールにプロセス名の条件がないときは取らない。取れないとき（管理者権限のプロセスなど）は空とし、プロセス名の条件には一致しない。プロセス ID は使い回されるので、結果を覚えるときの鍵は「プロセス ID とプロセスの開始時刻」にする。
- UWP アプリは、フレーム（`ApplicationFrameWindow`）のプロセス名が `ApplicationFrameHost.exe` になる（実機未確認）。UWP をプロセス名で指定しても、アプリごとには分けられないので、クラスかタイトルで指定する。設定画面の「ウィンドウを選んで追加」では、取れた値をそのまま入れ、UWP のときは注意を表示する。
- タイトルは判定のたびに現在の値で調べる（ブラウザのタブで変わる）。ドラッグとリサイズの途中では、開始時の判定を保つ。
- 正規表現は線形時間のもの（`RegexOptions.NonBacktracking`）で調べ、保存の前に検証する。書式が不正なルールは保存できない（画面にエラーを出す）。ファイルが手で書き換えられて不正になっていた場合は、そのルールを無効として扱い、ほかのルールには影響させない。
- 標準の動作を変えるものではないので、OS の設定は触らない。

**保存**

- ポータブル設定に `WindowRules`（配列、既定は空。各項目は有効、プロセス名、クラス、タイトルの正規表現、配置の扱い、角）を足す。スキーマ版を 11 から 12 に上げ、版 11 以下は空で読む。未来の版は既存どおり読み取り専用にする。同期・エクスポートの対象で、衝突は他のポータブル設定と同じ扱い（§12）。
- 設定は保存後すぐ本体に反映される（本体は settings.json を監視している）。

**設定画面**（モックアップ `docs/mockups/snapwell.html` の「アプリのルール」）

- 一覧: 有効のスイッチ、条件の要約、配置（タグ）、角（タグ）、並べ替え（上へ・下へ）、編集、削除。一覧の下に、読み取り専用で折りたたんだ「Snapwell が最初から対象外にしているもの」を置き、判定の順序の 1 に当たるものを示す（モックアップの旧案では「対象外（既定）」の行として一覧に混ぜていたが、編集・削除できないので分けた）。
- 「ルールを追加」: ダイアログに、プロセス名・ウィンドウ クラス・タイトル（正規表現）の入力欄と、配置の扱い（ラジオ 4 つ）と、ウィンドウの角（5 つから選ぶ）。「対象外」を選んだときは、角がまだ「全体設定に従う」なら「Windows の既定」にそろえる（変更できる）。何も決めないルールは追加できない。入力中に「いま一致するウィンドウ: N 件」を出し、一致したウィンドウの名前を見られる。
- 「ウィンドウを選んで追加」: 開いているウィンドウの一覧（タイトル、プロセス名、クラス）から 1 つ選ぶと、その値が入った状態で「ルールを追加」のダイアログが開く。クリックで指定する方式は、フックを増やさないために作らず、一覧から選ぶ形にする。
- 設定画面はウィンドウの列挙に公開 API（`EnumWindows`）だけを使う。

**テストの観点**

- Core: 一致の判定（条件の組み合わせ、大文字小文字、正規表現、順序、無効のルール、条件なしと何も決めないルールの拒否、不正な正規表現）、配置と角が別々に決まること、スキーマの移行、200 件の上限。
- Platform: 窓口の結果（常に対象外が強制より優先されること、位置だけと全体設定の関係）。プロセス名の取得は偽の API で試す。
- 実機で確かめる（MANUAL_TEST）: 管理者権限・UWP のプロセス名、ピクチャー イン ピクチャーに位置だけが効くこと、ルール追加の直後に反映されること、ブラウザのタブの切り替えでタイトルの条件が追従すること、全体設定が「角丸を強制する」でも、角を「Windows の既定」にしたウィンドウの枠（浮かぶチャットバーなど）が消えること、ルールの削除で角が戻ること。

**この版で作らないもの**: 操作ごとの対象外、モニターごとのルール、ルール単位のインポート・エクスポート、クリックでウィンドウを指す方式、`WindowRules` の同期での項目単位の統合（ファイル単位のまま）。

## 11. スタートアップ（R7）

| 方式 | 用途 |
|---|---|
| MSIX の `StartupTask` | ストア版・MSIX版の標準 |
| `HKCU\...\Run` | ポータブル版 |
| タスクスケジューラ（ログオン時、最上位の特権で実行） | 管理者権限のウィンドウも操作したい場合 |

設定GUIで「自動起動する」「管理者として起動する」を切り替える。
ポータブル版の自動起動は設定画面の「一般」で切り替える。状態は Run キーとタスクの実際の登録を正とし、同期対象の設定ファイルには入れない。

管理者起動は公開 COM API `ITaskService` / `ITaskFolder.RegisterTask` に XML を渡し、
`\Snapwell-<SID>` を登録する。`<SID>` は現在のユーザーの SID に置き換える。
同じユーザーの既存タスクは先に削除し、`TASK_CREATE` だけで新規作成する。削除後に同名を作られた場合は失敗にする。
所有者 Administrators、継承なしの DACL（SYSTEM と Administrators のフルコントロール、現在のユーザーの読み取りのみ）を SDDL で指定する。
CsWin32 の `allowMarshaling:false` による unmanaged COM 呼び出しを使う。
現在のユーザーの SID を LogonTrigger と Principal に指定し、InteractiveToken / HighestAvailable で実行する。
Principal の子要素は UserId、LogonType、RunLevel だけにする。XML の version は 1.3 とする
（[Microsoft のスキーマ](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema)）。
RequiredPrivileges に `SeImpersonatePrivilege` を入れると、タスク スケジューラが 0x80041316 で登録を拒否する（ARM64 実機で確認）ため指定しない。
指定がないタスクでは ERROR_PRIVILEGE_NOT_HELD (1314) になりうる（仕様からの推論、実機未確認）。
実行パスは本体の完全パス、作業フォルダーは本体のフォルダーとする。バッテリーでの開始・継続を許可し、
時間制限なし（PT0S）、IgnoreNew、StartWhenAvailable=false、AllowHardTerminate=true、Hidden=false とする。
状態の読み取りは昇格せず、タスクがなければ Off、Exec の Command が現在の exe と一致すれば On、別の場所なら Elsewhere とする。
Principal と LogonTrigger の UserId のどちらかが自分の SID と違う場合は、自分の登録ではないため Off とし、削除も置き換えもしない。
旧名 `\Snapwell` の登録には自動で触れない。

設定画面は通常権限のまま、`ShellExecuteEx` の runas で
`Snapwell.exe --set-admin-task on|off --for-sid <SID>` を起動し、終了コードを待つ。
ヘルパーは Mutex・トレイ・フックを作らず、登録と削除だけで終了する。
実行パスを引数で受け取らず、自身の `Environment.ProcessPath` だけを登録する。
昇格後のユーザー SID が指定した SID と違う場合は登録せず失敗とする（別の管理者の資格情報での昇格は不可）。
終了コードは 0:成功、1:失敗、2:SID 不一致、3:保護されていない場所。
実行パスは `Path.GetFullPath` で一度だけ正規化し、その結果に `%` がある場合は、
Task Scheduler の環境変数展開で検証先と実行先が変わるため拒否する（終了コード 4）。
8.3 の短い名前の展開で `%` が現れる場合も、XML 生成、画面のオン判定、昇格ヘルパーのすべてで拒否する。
正規化結果は `TaskExecutablePath` に保持し、ヘルパーの検査、保護された場所の判定、
XML の Command と WorkingDirectory に同じ文字列を使う。検査後は再び正規化しない。

オンにできるのは、exe と親フォルダーを管理者以外が書き換えられない場所（Program Files など）だけ。
ローカル固定ディスク（GetDriveType が DriveType.Fixed）に限り、UNC・ネットワークドライブ・リムーバブル・光学・RAM ディスクは拒否する。
Platform がドライブ種別と exe からルートまで各階層の再解析属性・ACL を読み、Core が保守的に判定する。
SYSTEM・Administrators・TrustedInstaller 以外の書き込み許可、上位フォルダーからの削除・差し替え、
不明な DACL・ACE、reparse point は拒否する。画面と昇格後のヘルパーの両方で確かめる。
読み取り不能や保護されていない場所では、オンにできない理由を表示する。既存の登録をオフにすることはできる。

Core の StartupMode は None / Normal / Admin。管理者オンは自動起動オンとして表示する。
管理者オンの前に元の Run の値を `%LOCALAPPDATA%\Snapwell\startup-run.txt` に退避し、
登録成功後だけ Run の値を外す。管理者オフでは、元が Run でオンだった場合だけ元の値を戻す。
自動起動全体をオフにした場合は両方式を削除し、元の Run には戻さない。
両方登録されている場合は Admin を優先し、画面を開いただけでは Run を消さない。
UAC キャンセルでは既存の登録を変えず、表示を戻す。ヘルパーの失敗では Run を外さないが、既存タスクの削除後の作成失敗ではタスクが未登録になることがある。
Run の操作が失敗した場合も退避情報を残し、実際の登録を読み直してエラーを表示する。
退避は版付き JSON で、元の Run がない状態も記録する。書き込み後に読み戻して確認できるまで、ヘルパーの起動と Run の削除を行わない。
復元待ちの退避は再オンでも上書きせず、復元成功後（または利用者が自動起動全体をオフにした後）だけ削除する。
タスク削除後の Run 復元失敗は画面に表示し、次の管理者オフで再試行する。壊れたファイルや旧形式はそのまま残し、読み取り失敗として操作を止める。

本体が昇格しているかは公開 API GetTokenInformation(TokenElevation) で確認する。
昇格している場合、設定画面は同じ SID の非昇格シェルトークンを DuplicateTokenEx で複製し、CreateProcessWithTokenW で起動する。
既存の `--setup` 引数も C ランタイムの規則で引用して渡す。シェル不在・SID 不一致・昇格シェル・API 失敗では起動を中止し、昇格した設定画面にフォールバックしない。
昇格処理中は両トグルを無効にする。表示の書き戻しは Toggled の呼び出しが戻った後に行い、アニメーションへの再入を避ける。
「Windows の確認画面が表示されます。次のサインインから有効です」と説明し、オンの成功時は
「次のサインインから管理者として起動します」と表示する。起動中の本体は変更せず、再起動ボタンは設けない。

**OS 設定の復元との関係:** §3.2 の原則 4（OS 設定を変えたら元に戻す）の例外として、Run とタスクの自動起動の登録は終了しても消さない。登録と削除は利用者が設定GUIで切り替えたときだけ行う。開発中のビルドでの登録はユーザーの指示があった試験だけに限り、試験後は削除して Run の値と `schtasks /Query /TN "Snapwell-<SID>"` で確認する。テストでは偽の Run キーとタスクサービスを使う（CLAUDE.md の「守ること」）。

## 12. 設定（R8・R9）

### 12.1 保存形式

- JSON（スキーマのバージョンを持たせ、古い形式から自動で移行する）。保存先は `%APPDATA%\Snapwell\settings.json`。
- **ポータブル設定**（ホットキー、分割案、間隔、操作感、アプリごとのルール）と、**端末固有の状態**（モニター構成ごとの配置、標準スナップの退避値）を別ファイルに分ける。同期とエクスポートの対象はポータブル設定だけにする。
- スキーマの版 2 で OpenLauncher の既定のキーを移行した。本体は settings.json を監視して取り込む。通常の編集は設定画面が保存し、同期からの取り込みでは本体も保存する。
- 現在のポータブル設定のスキーマは **版 9**。版 6 以下の既存値を保ち、LauncherPresets には既定の 8 個を入れる。版 7 の空配列は維持する。版 8 で足した MoveFixedSizeWindows（サイズ固定のウィンドウも動かす。既定オン）は、版 7 以下のファイルではオンとして読む。版 9 で足した MovePopupWindows（ポップアップとフライアウトも動かす。既定オン）は、版 8 以下のファイルではオンとして読む。オフにすると、ポップアップはドラッグの吸着・ホットキーの前面ウィンドウ・ランチャーの対象から外れる（整列と隣接吸着は設定にかかわらず含めない）。設定画面の「一般」ページの「対象のウィンドウ」にあるトグルで切り替える。版 10 以上は読み取り専用で保護し、保存・書き出しで上書きしない。設定画面の「一般」ページの「対象のウィンドウ」にあるトグルで切り替える。MoveFixedSizeWindows をオフにすると、サイズ固定のウィンドウはドラッグの吸着・隣接吸着・ホットキーの整列・ランチャーの整列の対象から外れる（角の設定は見た目なので対象のまま）。
- 見た目の設定は `CornerPreference`（Windows の既定／角丸を強制する／小さい角丸／角丸なし。既定は変更しない）、`ShowZoneLines`（区画の線、既定オン）、`ShowPredictionLine`（投げた先への予測線、既定オン）。大きな半径の角丸（macOS 風）は採用しない。
  投げたウィンドウの吸着先の区画と予測の線は、ドラッグ中は出さず、離した瞬間から着地の動きが終わるまで（最短 150 ms、最長 2 秒）出す。実機で「動かしている間に出す案」と比べ、これに決めた（止めても残る、投げると一瞬しか出ない、を避けるため）。予測の線の終点は、慣性の位置ではなく着地する区画のタイトルバー。設定の版 10 は、この見せ方の選択肢を一度出して取り下げた版。
  手動リサイズでは `SnapAfterResize` がオンのとき、操作中から離したときに揃う区画を青く塗り、離したあとも着地まで残す（着地の監視は 50 ms 間隔、最短 150 ms、最長 2 秒）。予測の線は出さず、区画の点線枠は `ShowZoneLines` に従う。`ShowZonePreview` がオフなら、投げた場合も手動リサイズも表示しない。描画は既存の `IOverlayPresenter.Request` に渡す。
- グリッドの設定は共通の `Grid`・`Gap`・`Edge` に加え、`MonitorGrids`（識別子 → 列数・行数・任意の間隔と余白。既定は空）を持つ。識別子は現在の `MonitorInfo.DeviceName`。大文字小文字を区別せず、未設定のモニターでは共通値を使う。表示番号が変わる接続変更は設定を選び直す必要がある。間隔と余白の未指定は共通値を使う。
- `SnapAfterResize`（既定オフ）は、手動リサイズの終了時に、中心のあるモニターの最寄りの区画境界へ揃える。最大化・最小化・サイズ固定・自プロセス・移動だけの操作は除外し、最小サイズを満たす区画範囲がない場合は移動しない。
  操作中は配送済みの `MouseMoved` ごとに現在の見た目の矩形を取得し、終了時と同じ `ResizeSnapPlanner.Plan` でプレビュー先を求める。対象となる通常ウィンドウの操作中は既存のドラッグ処理がマウス移動の配送を有効にするため、矩形の定期取得は追加しない。同じ目標なら再描画せず、計画がなくなれば消す。開始時と現在のウィンドウ DPI・中心のあるモニターの DPI が一致しない場合も計画しない。分割案や間隔は更新ごとに読み直す。
  リサイズ終了時に計画があれば、表示を消さず既存の物理モデルへ移動を要求する。着地監視はドラッグと同じ猶予・上限を持ち、動きの継続時間は固定しない。ドラッグとリサイズには表示元ごとの窓口を渡し、ドラッグ側の終了処理でリサイズの区画を消さない。計画なし・対象の破棄・キャンセル・別の操作の開始・一時停止・設定変更によるランタイムの差し替えでは表示を消す。着地待ちも設定の無効化、対象の不適格化、DPI・モニター構成の変化を監視して消す。
- 角の変更前の値と対象プロセスの識別は `%LOCALAPPDATA%\Snapwell\corners.json` に退避する。既定へ戻すとき、無効化、終了、次の起動で復元し、復元に失敗した記録は残す。他プロセスに対する見た目の効果は実機未確認。

### 12.2 インポート・エクスポート

- 設定GUIからファイルに書き出し、読み込む。読み込み時には差分を表示し、全体を置き換えるか一部だけ取り込むかを選べるようにする。

### 12.3 クラウド同期（段階的に導入）

| 段階 | 方式 |
|---|---|
| 1（実装済み） | 利用者が選んだ同期フォルダー（OneDrive、Dropbox など）の `snapwell-settings.json` を監視する。サーバー・アカウント・外部通信は使わない |
| 2 | アカウントを使った同期（GitHub Gist など）。必要性を見て判断する |

- **Snapwell 自体にクラウド同期の機能はない。** 同期の実体は OneDrive・Dropbox などの第三者のファイル同期サービスで、Snapwell は選ばれたフォルダーのファイルを読み書きするだけ。そのため、サービスの同期が終わるまで他の PC には届かないことを、設定画面の「同期とバックアップ」に注意書きとして出す。
- 同期ファイルは `settings.json` と同じ PortableSettings の JSON。`device.json` と OS 設定の退避値は同期しない。
- 端末状態の版 3 に `SyncFolder`（未設定は null）、`SyncEnabled`（既定オフ）、`LastSyncUtc`、`LastSyncedHash` を保存する。版 2 以下では同期はオフ・未設定。フォルダーの選択とオン・オフは、この PC に即時保存する。
- 読み込み・移行・正規化後の JSON はオブジェクトのキーを整列して SHA-256 で比較する。同じ内容は書き直さず、片側がなければもう片側から作る。両方なければ何もしない。
- 前回の一致ハッシュと比べ、一方だけが変わった場合は変更された側を採る。初回の不一致または両側の変更では更新時刻が新しい側を採り、同時刻ならローカルを採る。PC 間の時計のずれは解消しない。
- 上書きする側は必ず先に `%LOCALAPPDATA%\Snapwell\sync-backups` へ `settings-<UTC の yyyyMMddTHHmmssfff>-local.json` / `-remote.json` として複製する。種類ごとに新しい 10 個を残す。バックアップ失敗時は上書きしない。
- 新しい版はどちらも保護する。ローカルの破損では同期を見送る。同期先の破損だけはバックアップ後に正常なローカルで修復する。4 MiB を超えるファイルは失敗として保持する。
- 設定の保存フォルダーと同じ、その中、または親の同期フォルダーと、設定ファイル自体を同期先にする選択は拒否する。判断中に内容が変わった場合も失敗とし、上書きしない。保存は同じフォルダーの一時ファイルから原子的に置き換える。
- 最新の端末状態の読み込みから成功の記録までと設定画面の通常保存は同じ Mutex で排他し、置換直前に再検証して退避するが、外部の書き手による最終検証から置換までの変更は完全には排他できない。
- 本体と設定画面は同じ名前付き Mutex で同期を直列化する。処理はバックグラウンドで実行し、同期フォルダーを自動作成しない。本体は起動、設定・同期ファイルの変更、同期のオン・フォルダー変更で実行する。監視は 300 ms の収束待ち、失敗と Busy の再試行は 30 秒後に 1 回だけとする。
- 設定画面は取り込みを検知し、未保存の変更がなければ再読み込みする。変更があれば保持し、同期ページで「保存すると取り込んだ内容を上書きする」と知らせる。

## 13. 角丸（R10）

| 方式 | 内容 | 評価 |
|---|---|---|
| DWM の角設定 | `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` で角丸、小さい角丸、角丸なしを指定する | Windows 11標準の仕組みで、影も保たれる。ただし**半径は固定**（約8px）。他プロセスのウィンドウに適用できるかは要検証 |
| ウィンドウ領域 | `SetWindowRgn` で角を切り取る | 半径は自由に決められるが、ギザギザになり、DWMの影が消える。アプリと干渉しやすいので非推奨 |
| オーバーレイで覆う | 角の部分を背景で覆うマスクを重ねる | 半径は自由だが、背景と合わせ続けるのが難しい |

**方針:** まずDWMの角設定を「角丸を強制する」機能として実装する（Windows 11の既定で角丸にならないウィンドウにも適用する）。ただし、フレームなしで浮かぶウィンドウ（Claude のチャットバーなど）に強制すると四角い枠が出ることを実機で確認した。DWM の角の設定は、DWM が枠を描くウィンドウにだけ意味があるため、タイトルバー（`WS_CAPTION`）もサイズ変更の枠（`WS_THICKFRAME`）もないウィンドウには適用しない（チャットバーは `WS_CAPTION`・`WS_THICKFRAME` なし、`WS_EX_TOPMOST` ありで、サイズ固定に分類されていた）。この基準で外れたウィンドウに角を当てたいときや、枠のあるウィンドウだけ個別に変えたいときは、アプリごとのルール（§10.4）で上書きする。macOS 相当の大きな半径は、実現方法が見つからず、採用しないと決めた（2026-10-20）。

## 14. 非機能要件

| 項目 | 目標 |
|---|---|
| 応答性 | ホットキーを押してから配置が終わるまで50ms以下（アニメーションなしの場合） |
| アニメーション | ディスプレイのリフレッシュレートに同期する（`DwmFlush` などで待つ）。演算は240Hzの固定ステップ |

| 安全性 | OS設定を必ず復元できる（§8）。クラッシュ後の自動復旧 |
| 多言語 | 日本語・英語 |
| ライセンス | feel（MIT）のアルゴリズムを移植する場合は著作権表示を同梱する。本製品のライセンスは別途決定する（業務利用を明確に許可する方針） |

## 16. モックアップ作成の対象画面

次の工程で作るモックアップは以下を想定する。

1. **ランチャー**（グリッドのオーバーレイ、範囲選択、プリセット、ウィンドウのサムネイル）
2. **スナップ中の表示**（投げたウィンドウの軌跡、予測される停止先の区画のハイライト）
3. **設定GUI**（一般、分割と間隔、ホットキー、操作感（feel のプリセットとパラメーター）、アプリごとのルール、標準機能の制御、同期とインポート・エクスポート、ランチャー（プリセット選択）、外観（角丸））
4. **トレイメニュー**（ヘッダーのスイッチで実行・一時停止を切り替える。項目は「現在のモニターを整列」「ランチャーを開く」「設定を開く」「終了（標準の動作に戻す）」の 4 つで、ホットキーは表示しない。ヘッダーのアイコンとタグは有効・一時停止中・異常の 3 種で、タグの幅は文言に合わせる。異常を最優先し、異常中に一時停止しても「異常」を保つ。プロファイルの切り替えは未実装）
5. **初回セットアップのウィザード**（標準スナップの停止への同意、ホットキーの確認、分割案の選択）
