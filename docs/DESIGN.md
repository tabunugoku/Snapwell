## 1. 目的とポジション

製品名: **Snapwell**（Snap ＋ 磁石のポテンシャルの「井戸」。投げたウィンドウが区画に吸い込まれる挙動から）

業務PCで、ドック着脱やスリープを含む日常的な環境変化の中でも壊れず、GUIで設定できるウィンドウマネージャーを作る。物理挙動に基づく気持ちのよいスナップ（投げたウィンドウが角や区画に吸い込まれる操作感）を特徴とする。

競合調査で挙げた勝機との対応は次のとおり。

| 勝機 | 本設計での対応 |
|---|---|
| 業務利用を明確に許可するライセンス | ライセンス方針は別途決定（§13） |
| GUIで完結し、ホットキーを内蔵 | ホットキー、ランチャー、設定GUIを本体に内蔵する（§6, §9） |
| モニター構成の変化に強い | モニター構成ごとに状態を保存・復元する（§10.3） |
| Windows更新への耐性 | 非公開APIを使わず、DLLインジェクションもしない（§3.2） |

### 3.1 プロセス構成

### 3.2 設計原則

1. **DLLインジェクションをしない。** フックは `SetWinEventHook(WINEVENT_OUTOFCONTEXT)` と低レベルフック（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`）だけを使う。他プロセスへコードを注入しないため、対象プロセスのアーキテクチャ（x86、x64、ARM64、エミュレーション中のx64）と関係なく動き、x86版を作らない方針（R1）とも矛盾しない。
2. **非公開APIに依存しない。** 仮想デスクトップの非公開COM APIは使わない。ワークスペースが必要になった場合は自前で実装する。
3. **時間ではなく物理でアニメーションする。** 移動アニメーションは feel と同じく、質量・剛性・減衰から導く。継続時間やイージングを固定値で決めない（§5）。
4. **OS設定を変えたら必ず元に戻す。** 標準スナップの停止など、OS設定を変更する場合は変更前の値を保存し、終了時やクラッシュ後の再起動時に復元する（§8）。
5. **Per-Monitor DPI Aware v2 で動かす。** 座標はすべて物理ピクセルで扱う。

## 4. 技術スタック（推奨案）

| 項目 | 推奨 | 理由 |
|---|---|---|
| 言語・ランタイム | C# / .NET 9 以降、NativeAOT | x64・ARM64 のネイティブバイナリを1つのコードベースから出力できる。起動が速く、常駐時のメモリも小さい |
| Win32 相互運用 | CsWin32（ソースジェネレーター） | 型安全なP/Invokeを生成できる |
| 設定GUI | WinUI 3（Windows App SDK） | Windows 11標準の見た目。x64・ARM64対応 |
| オーバーレイ（ランチャー、区画プレビュー） | Win32 レイヤードウィンドウ ＋ DirectComposition / Direct2D | 透過・最前面・クリック透過・高リフレッシュレートでの描画に向く。WinUI 3は透過オーバーレイが苦手 |
| 配布 | MSIX（x64・ARM64のバンドル）＋ winget、ポータブル版のzip | 法人での配布（Intune）と個人での導入の両方に対応する |
| ビルド対象 | `win-x64`、`win-arm64` | **x86（`win-x86`）は作らない**。CIで両アーキテクチャをビルドし、ARM64の実機でテストする |

代替案: Rust（windows-rs）でコアを書き、GUIを別技術で作る構成。性能面では有利だが、GUIとの連携の手間が増えるため第一候補にはしない。

## 5. スナップ物理モデル（feel「03 · Card thrown to a corner」の移植）

### 5.1 元実装の要点（diip3sh/feel, MITライセンス）

| 要素 | feel での仕様 |
|---|---|
| モデル | 質量 m・剛性 k・減衰 c を持つ2次元の物体（`Body2D`）。ばねは両軸で同じ定数を使う（等方性）。壁は軸ごとに設定する |
| 言葉から数値へ | `Feel.words("airy, slightly magnetic")` が質量・固有振動数 f・減衰比 ζ を返す。k = m·(2πf)²、c = 2ζ·√(k·m) |
| ドラッグ | 座標を直接書き換えず、手（ポインタ）への「ハンドばね」の目標を更新する。重い物体ほどポインタから遅れる |
| リリース | 速度を保ったまま手を離す。惰性で止まる予測点は **x + v·m/c**。最終的な停止先は「惰性で止まる場所」から決め、ミリ秒の閾値は使わない |
| 停止点 | 4隅（時計回りに 0:左上、1:右上、2:右下、3:左下）。磁石場の強さは feel の語彙から決まる（magnetic = 1、clicky = 0.6、tactile = 0.5、「slightly」は 0.5 倍。語がなければ corner-card の既定の 0.6）。力は、最寄りの停止点への弱く遠くまで届くばね（吸い寄せの振動数 0.6 + 0.5×強さ）に、吸着半径の内側で滑らかに効く強いばね（吸着（クリック）の振動数 3 + 4×強さ）を足したもの。力 = −m(2π·reach)²·u − m(2π·click)²·u·smoothstep(1 − \|u\|/半径)。吸着半径（clickRadius）は corner-card では 28px（ライブラリの既定は 1 次元 18、平面 24） |
| 壁 | 可動範囲の端（0〜W、0〜H）を壁にし、行き過ぎを描画しない |
| 中断 | 移動中につかみ直すと、現在の位置と速度から続ける。速度をリセットせず、アニメーションをキューに積まない |
| フリック | 現在の角の対角（index+2）へ、指定した速さで弾く |
| 浮き上がり表現 | lift = min(1, 速さ/3000)。拡大率 1+0.05·lift、影のオフセット 4+16·lift、ぼかし 12+28·lift |
| 演算 | 全物体で1つのフレームループを共有し、全物体が静止したら止める。シミュレーションは240Hz |

### 5.2 ウィンドウへの適用

```
ユーザーがタイトルバーをドラッグ
  └─ EVENT_SYSTEM_MOVESIZESTART を検知 → 追跡を開始（ポインタの位置と時刻をリングバッファに記録）
ユーザーがマウスボタンを離す
  └─ EVENT_SYSTEM_MOVESIZEEND
       1. 直近 50〜80ms の軌跡から離した瞬間の速度 v を推定する
       2. 予測点 p = x + v·m/c を計算する
       3. p に最も近いスナップ先を選ぶ（候補: 四隅・半分・グリッド区画、§5.3）
       4. 速度が閾値未満で、予測点がスナップ先の吸着半径の外にある場合は何もしない
          （通常の移動として扱う）
       5. ばね・磁石場・壁のシミュレーションでウィンドウを停止点まで移動する
       6. 静止したら、最終的な矩形（サイズを含む）を確定する
```

- **壁:** 作業領域（タスクバーを除く領域）を壁にする。feel と同じく、壁は硬く減衰の効いたばね（剛性 m(2π·8)²、減衰比 0.9、押し込むときだけ減衰）で、止めるのではなく押し返す。そのため、非常に速い投げでは壁を数 px 越えてから戻る。停止点（余白 §6.3 を引いた位置）は壁の内側にある。
- **マルチモニター:** 予測点が隣のモニターの作業領域に入る場合はそのモニターのスナップ先を候補に含め、モニター間の境界では壁を作らない。
- **中断:** 移動中にウィンドウを再びつかんだ場合（`EVENT_SYSTEM_MOVESIZESTART` またはマウスダウン）は、シミュレーションを即座に止め、制御をユーザーに返す。
- **操作感のプリセット:** 設定で feel の語彙（例: 「airy, slightly magnetic」「heavy」「snappy」）を選べるようにし、詳細設定では m・f・ζ・磁石の強さを直接調整できるようにする。
- **磁石の強さと吸着半径（feel の磁石場の移植）:** `WindowBody` は feel の Body2D と同じく RK4・刻み 1/240 秒で動き、停止点を持つときは目標へのばねを使わず、磁石場の力 −m(2π·reach)²·u − m(2π·click)²·u·smoothstep(1 − |u|/半径)（u は最寄りの停止点からのずれ）で動く。減衰係数 c = 2ζ√(km) には語の固有振動数から導く k を使うが、力としては使わない。質量・固有振動数・減衰比は §5.1 の語彙（`FeelWords`）から決まり、設定画面のカードの語は airy, slightly magnetic ／ snappy, precise ／ heavy, settled ／ light, playful。磁石の強さは語から決まり（airy, slightly magnetic は 0.5、磁石の語がなければ 0.6）、設定で上書きできる（0〜2。feel の語は "super magnetic" で 1.8）。吸着半径の既定値は corner-card の 28px（物理ピクセルへは対象モニターの拡大率で換算）。手を離したあとの予測点は p + v·m/c。四隅モードは 4 つの角を停止点とした場の中を、離した速度のまま 6 秒を上限に動かして止まる角を選ぶ（feel の predict）。
- **区画の選び方（feel にない Snapwell 独自の部分と、場で決める部分）:** 区画モードでは、(1) 候補の絞り込みは Snapwell 独自のルール（モニター、最大化の条件、上下の行を決める 30%/70% の帯とカーソルの帯、隣の辺 24px）。最大化と隣の辺は候補が一つで、ルールの結果がそのまま選ばれる。(2) 残る左右の二候補は feel の磁石場で決める。窓の中心を、二つの区画の中心を停止点とする場の中で、離した速度のまま最大 6 秒動かし、止まった側を選ぶ。そのため、予測点（p+v·m/c）が反対側にあっても、手前の停止点に引き戻されれば元の側に止まる（feel の「勢いで決まる」）。(3) 選んだあとは、その区画の左上の一点を停止点とする場でウィンドウを動かす。feel に区画（矩形・サイズ）はないので、停止点は左上の一点にし、サイズは静止を確定したときに目標へ合わせる。
- **操作感の自由編集（カスタム）:** 4 つのプリセットは土台で、質量（0.15〜8）・固有振動数（0.4〜7 Hz）・減衰比（0.1〜1.6）・磁石の強さ（0〜2）は手で変えられる。範囲は feel の rig のスライダー（質量・振動数・減衰比）に合わせ、磁石の強さと吸着半径（8〜96）は Snapwell の設定。保存は「プリセット名（Feel）＋手で変えた値だけの上書き（`Mass`・`Frequency`・`DampingRatio`・`MagnetStrength`、未指定は null）」で、スキーマ版は 4 のまま（欠けた値は null で読むため、旧い版のファイルはプリセットのまま読める）。プリセットを選ぶと 4 つの上書きがすべて消え、値が表示上（小数 2 桁）プリセットと同じなら上書きにしない。上書きが一つでもあれば「カスタム」。取り込みの範囲外の値は、クランプではなくプリセットの値に戻す。**質量は、磁石場の力・壁・減衰がすべて質量に比例するため、吸着の動きを変えない**（feel でも、質量が効くのは手のばねと摩擦だけ）。k・c の表示にだけ効く。設定画面の「試す」は Core の `FeelTrial` で動かす。舞台を一つのモニターと見なして本体の `SnapResolver`（足切り・最大化の条件・左右の二候補を場で決める・四隅）に吸着先と停止点を決めさせ、動きは本体と同じ `WindowBody`。試す領域だけの規則は持たない。つかめるのはタイトルバー（高さ 30 px。実物より大きめ）だけで、判定は `FeelTrial.HitsTitleBar`（左と上の辺は含み、右と下は含まない。タッチとペンは四方へ 8 px 広げる）。
- **feel にない独自の扱い（そのほか）:** 隣の辺への吸着距離は論理 24px の固定値で、吸着半径とは別。速度 150px/s 未満は吸着しない（通常のドラッグと投げを分けるための、feel にない独自の足切り）。ホットキーの移動は feel の to(p)（目標へのばね）。物理の刻みは 1/240 秒、1 フレームの上限は feel のループと同じ 1/30 秒。設定画面のカードの曲線は feel の response()（閉形式）。
- **アクセシビリティ:** OSの「アニメーション効果」がオフ、またはアプリ設定でモーション削減が有効な場合は、停止点へ即座に移動する。

### 5.3 スナップ先（停止点）の候補

| 種類 | 内容 | 既定 |
|---|---|---|
| 四隅 | 現在のサイズのまま作業領域の四隅に置く（feel と同じ） | 有効 |
| 半分・四分割 | 左右・上下の半分と4分割 | 有効 |
| グリッド区画 | §6 のグリッドに揃えた位置。サイズは維持するか、投げた方向の区画に合わせるか選べる | 設定 |
| 最大化 | 上端への強いフリック | 設定 |

候補が多いと誤吸着が増えるため、候補点ごとの磁石の強さと吸着半径を持たせる。

区画モードでは、離した時点（プレビューでは現在）のカーソルが、対象モニターの作業領域の
上端に押し付けられていれば上の四分割、下端に押し付けられていれば下の四分割を選ぶ。
端の帯は、内側を論理 12px（対象モニターの拡大率で物理ピクセルへ換算）、外側を作業領域の高さの 10% までとし、
いずれも境界を含む。内側は端の近くのタイトルバーと押し付けたカーソルを分け、外側はタスクバー上のカーソルを拾う。
カーソルの X が作業領域の左端以上・右端未満のときだけ、この帯を使う。
外側の帯は、カーソルがほかのモニターの作業領域内にある場合は使わない。作業領域の包含は左端・上端を含み、
右端・下端を含まない。対象モニター自身の作業領域内にある内側の帯は従来どおり使う。
端に付いた背の高いウィンドウも、中心の高さに左右されず四分割にできるようにする。
帯の外や X の範囲外、ほかのモニター内の外側の帯、カーソル位置がない場合は、予測したウィンドウ中心による上下 30% の判定を使う。
左右と対象モニターは従来どおり予測中心で決め、上中央への強い投げによる最大化を四分割より優先する。
四隅モードはカーソル位置を使わない。

### 5.4 移動の実装方式（要検証）

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A: 直接移動 | 毎フレーム `SetWindowPos(SWP_NOSIZE \| SWP_NOZORDER \| SWP_NOACTIVATE \| SWP_ASYNCWINDOWPOS)` を呼ぶ | 実装が単純で、どのウィンドウにも使える | 再描画の遅いアプリではカクつく。拡大・影などの浮き上がり表現はできない |
| B: 代理描画 | `DwmRegisterThumbnail` でウィンドウの縮小像を自前のオーバーレイに表示してアニメーションし、静止時に実際のウィンドウを1回で配置する | 高リフレッシュレートで滑らか。浮き上がり表現（拡大・影）を再現できる。サイズ変化も滑らかに見せられる | 移動中に元のウィンドウを隠す手段に制約がある（他プロセスのウィンドウはクローキングできない） |

**方針:** 既定はAとし、Bは技術検証（スパイク）で実現性を確かめてから「高品質モード」として追加する。サイズ変更はアニメーションせず、静止時に1回だけ適用する（再描画の負荷を避けるため）。

**検証の結果（`docs/SPIKES.md`）:** 位置の `SetWindowPos` は 1 回 1 ms 未満で、60 Hz で動かせる。サイズの変更は 1 回 24〜27 ms かかり、毎フレームは無理。Bは、他プロセスのウィンドウのサムネイルを描けること、元のウィンドウを画面外へ移動しても（またはレイヤード＋透明度 0 にしても）サムネイルが描かれ続けることを確認した。隠す方法は、副作用の少ない「画面外へ移動」を第一にする。

## 6. 画面分割（R2・R4）

### 6.1 グリッドモデル

- モニターごとに**分割案**（列数 N × 行数 M）を持つ。例: 8×8、12×6、6×4。既定は 8×8。
- 1区画を**基本単位**（unit）とする。ウィンドウのサイズは「横 a 区画 × 縦 b 区画」（a, b は正の整数）で表す。
- 区画の矩形は、間隔の設定（§6.3）を考慮して次の式で求める。

```
作業領域の幅 W、余白 e（画面端）、間隔 g（ウィンドウ同士）、列数 N のとき
  区画の幅 cw = (W − 2e − (N−1)·g) / N
  横 a 区画のウィンドウ幅 = a·cw + (a−1)·g
  列 i（0始まり）の左端 x = e + i·(cw + g)
（高さも同様に計算する）
```

- 端数は 1 か所に寄せず、区画の幅の差が 1 px 以内になるよう分散させる。列 i の左端は `左 + e + floor(i·(W − 2e + g) / N)` とし、最後の区画の右端がちょうど `右 − e` になる（実装は `Snapwell.Core.Layout.GridLayout`）。

### 6.2 一定比率でのサイズ変更（R4）

| 操作 | 内容 |
|---|---|
| 倍率指定 | 基本単位の ×1、×2、×3…（例: 8×8 なら 2×2 区画＝画面の 1/16） |
| 段階拡大・縮小 | 横・縦・両方向に 1〜4 区画ずつ増減する（設定の `ResizeStep`）。固定する位置は左上・中心・近い辺（作業領域の端に近いほうの辺。軸ごとに決める）から選べる（`ResizeAnchor`） |
| プリセット比率 | 1/4、1/3、1/2、2/3、3/4 などを、分割案の区画数で表せる値として登録できる |
| 吸着 | 手動でリサイズしたあと、最も近い区画境界に揃える（任意） |

ウィンドウの最小・最大サイズの制約で区画に収まらない場合は、実際に適用されたサイズを読み直し、区画内で中央寄せ（または投げた方向の角に寄せ）して配置する。

### 6.3 間隔（R3）

| 設定 | 内容 | 既定 |
|---|---|---|
| ウィンドウ間隔 g | 隣り合うウィンドウの間のピクセル数 | 0（Windows標準と同じ隙間なし） |
| 画面端の余白 e | 作業領域の端とウィンドウの間のピクセル数 | g と連動（個別にも設定できる） |
| DPI スケーリング | g と e を論理ピクセルで指定し、モニターごとのDPIで換算する | 有効 |

**見えない枠の補正:** Windows 10/11 のウィンドウには、見た目の外側に約7pxの見えないリサイズ枠がある。`GetWindowRect` の値はこの枠を含むため、見た目の矩形は `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` で取得し、差分を補正して配置する。補正しないと間隔0でも隙間ができ、指定した間隔も正確にならない。

## 7. ウィンドウ整列（R3）

| 機能 | 内容 |
|---|---|
| グリッド自動整列 | 対象モニター上のウィンドウを、数に応じて行列に並べる |
| 列・行に整列 | 横一列、縦一列、メインと残りのスタック（マスター／スタック）型 |
| 隣接吸着 | ドラッグを離した予測位置が、隣のウィンドウの辺から論理 24 px 以内なら、その辺に g の間隔を空けて吸着する（サイズは変えない）。吸着方式が区画のときだけで、最大化の投げと、カーソルが画面の上端・下端の帯にあるときは区画を優先する。ドラッグ開始時に隣のウィンドウを一度だけ取り、プレビューと離したときで同じ一覧を使う。キー操作は前面のウィンドウを上下左右の最も近い隣の辺へ寄せる（下記） |
| 整列対象 | 現在のモニター／全モニター／選択したウィンドウ（ランチャーで複数選択。未実装で、当面は省く） |
| 間隔の適用 | すべての整列で g と e を適用する。g=0 のときは隙間なしでぴったり並べる |

キー操作の隣接吸着は、吸着方式によらず、指定方向の軸だけ位置を変え、直交する軸と幅・高さを保つ。
候補は、直交軸で正の長さだけ重なり、指定方向側に辺がある隣のウィンドウとする。
右方向なら `neighbor.X >= current.Right` の辺から g を引き、現在の幅を引いた X へ寄せる
（左・上・下も同様）。作業領域と交わらない隣や、方向側に辺がない重なった隣は無視する。
現在と同じ位置になる候補と、辺に寄せると作業領域の余白 e を侵す候補を除き、移動量が最小のものを選ぶ。
候補がなければ、その方向の作業領域の端から e 空けた位置へ寄せる。既に同じ位置なら何もしない。
移動軸の座標は余白内へ Clamp し、ウィンドウが大きすぎる場合はその軸の開始側の余白へ揃える。
g と e は対象モニターの DPI で物理ピクセルに換算する。隣の一覧は App の
`NeighborWindowSource.Snapshot(handle)` から Core の `AdjacentSnapPlanner` へ渡す。
サイズ固定も位置だけ動かし、最大化中は通常状態に復元してから計画する。移動には §5 の物理モデルを使う。
操作は `WindowCommand` の既存の整数値を保って末尾に追加する。既定のキーは Ctrl+Alt+Shift+J・L・I・K（左・右・上・下。Win は付けない）。
設定のスキーマ版は 5 とし、版 5 未満で操作が未割り当てかつ同じキーが未使用の場合だけ既定値を補う。

整列時の移動にも §5 の物理モデルを使う（設定でオフにできる）。複数のウィンドウは `BeginDeferWindowPos` でまとめて確定する。

- 物理演算は変更せず、フレームごとに計画した位置（Position）を `BeginDeferWindowPos` → `DeferWindowPos` → `EndDeferWindowPos` で一括確定する。対象が 2 つ以上のときだけバッチにし、1 つなら従来の `MoveVisual` を使う。`IWindowMover.ApplyBatch` と `IWindowPositionApi.ApplyBatch` の `positionOnly` が true のときは `SWP_NOSIZE` を付け、サイズ・Z 順序・フォーカスを変えない。
- 静止した対象の最終サイズ（Bounds）は従来どおり個別に適用し、実矩形を読み直す。Position と Bounds が混在するときは元の順序を保ち、Bounds の前後で連続する Position のバッチを区切る。
- モーション削減時は最終 Bounds を 2 つ以上まとめてサイズつきバッチ（`positionOnly=false`）で適用する。その後は対象ごとに実矩形を読み直し、最小・最大サイズの制約などで Walls をはみ出した場合だけ `MoveVisual` で寄せる。Walls より大きい寸法は Walls の左端・上端に合わせる。1 つの場合とバッチ失敗時は従来の個別経路を使う。
- バッチを組み立てる間はエンジンのロックを持ち、各対象のエントリーとバージョン（`IsCurrent`）を確認して、取り消し・差し替え済みの対象を外す。同じハンドルを 1 フレームに重複させない。外部 API はロックの外で呼び、返らない場合も取り消し・新規要求・終了を妨げない。確認直後から外部呼び出しまでの間の取り消しは、個別経路と同じく進行中の 1 回を止められない。終了後は新たな適用・読み直し・補正を開始しない。
- バッチが false または例外で失敗したフレームは、対象全員を元の順序で個別適用へ戻して再試行する。その際も対象ごとに `IsCurrent` を確認し、失敗した対象のエントリーだけを外す。サイズ適用はバッチからの再試行を除いて最終の 1 回とし、新しい要求のエントリーを古い結果で消さない。
- `WindowMover` は最大化した対象を既存の `TryPrepare` で復元し、通常状態の見えない枠を取り直して補正する。調査・復元が失敗または例外になった対象はバッチから除き、そのハンドル一覧を呼び出し側へ返す。残りの対象のバッチは続行し、全対象を除いた場合はネイティブ API を呼ばない。サイズつきのフラグと枠補正の扱いは従来どおりとする。

ホットキー操作では、前面のウィンドウがある現在のモニターを対象に、通常とサイズ固定のウィンドウを 4 つの方式（グリッド・横一列・縦一列・メインとスタック）で整列する。グリッドは `ceil(sqrt(count))` 列×`ceil(count/列数)` 行（縦長の作業領域では列と行を入れ替え、最後の行は残りのウィンドウで行幅を等分）、メインとスタックは前面のウィンドウを左半分・残りを右半分に縦等分する。並べる順は見た目の矩形の中心座標で決める（横一列は X、縦一列は Y、グリッドは Y の次に X、メインとスタックは前面のウィンドウを先頭にして残りを Y の小さい順）。既定のキーはグリッド整列が Ctrl+Alt+A（スキーマ版 3 で移行）、横一列・縦一列・メインとスタックが Ctrl+Alt+Shift+H・V・M、全モニターのグリッド整列が Ctrl+Alt+Shift+A（スキーマ版 4 で移行。同じキーが割り当て済みなら足さない）。全モニターの整列は、各モニターに属するウィンドウをモニターごとにグリッドで並べ、前面のウィンドウを先頭にしない。トレイメニューの「現在のモニターを整列」は、前面が Snapwell 自身になるため、カーソルがあるモニターをグリッドで整列する。ランチャーでの複数選択は未実装（当面は省く）。

## 8. Windows 標準機能との干渉防止（R6）

| 対象 | 制御方法（案） | 備考 |
|---|---|---|
| ドラッグでのスナップ（Aero Snap） | `SystemParametersInfo(SPI_SETWINARRANGING, FALSE)` | 設定アプリの「ウィンドウのスナップ」と同じ設定 |
| スナップレイアウト（最大化ボタンのフライアウト） | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced` の関連値 | 要検証。値の名前と効き方はWindowsビルドで変わる可能性がある |
| 画面上端のスナップバー（24H2以降） | 同上 | 要検証 |
| Win+矢印キー | 本ツールが有効な間だけ、低レベルキーボードフックで握りつぶして自前の操作に割り当てる | Explorerが予約しているため `RegisterHotKey` では登録できない |
| 他プロセスのウィンドウの角 | `DWMWA_WINDOW_CORNER_PREFERENCE`（§13） | 変更前の値を `corners.json` に退避し、既定へ戻したとき・無効化・終了・異常終了後の起動で復元する |

**安全策:**

1. 変更前の値を設定ファイルとは別の状態ファイルに保存する。
2. 正常終了時と無効化時に元の値を復元する。
3. 起動時に状態ファイルが残っていれば、前回は異常終了したと判断して復元する。
4. 設定GUIに「標準の動作に戻す」ボタンを置き、手動でも復元できるようにする。
5. 初回有効化時に、変更するOS設定の一覧を表示して同意を得る。

初回起動では、本体が設定画面を `--setup` で開き、「ようこそ → 標準機能 → ホットキー → 分割案」の
4 手順を案内する。本体は完了を待たずに常駐するが、標準スナップの停止は手順 2 の「次へ」で
`DisableStandardSnap` と `StandardSnapConsentGiven` を保存した後だけ行う。チェックを外しても先へ進める。
端末状態の保存を監視し、同意の変更を起動中の本体にも反映する。無効化・終了・異常終了後の復元は従来どおり行う。

ウィザードは通常の設定画面と別の単一インスタンスで、再起動要求では同じユーザーのウィザードを前面に出す。
途中で閉じる（Esc を含む）と未完了のままにし、次の本体起動で再表示する。スキップは設けない。
ホットキーは §9.1 の設定内の重複検出と Windows の一時登録の可否で確認する。重複があっても進められ、
未割り当ての操作はその状態を表示する。他アプリの低レベルフックによる横取りまでは判定できない。
最後に §6 の 8×8・12×6・6×4 と間隔 0〜24 px を選び、画面端の余白も同じ間隔にする。
既存ストアで最新の設定を読み直し、ほかの項目を保ったまま `settings.json` を保存してから
端末状態の `SetupCompleted` を true にする。保存失敗や未来の版で読み取り専用の場合は完了にせずエラーを示す。
端末状態のスキーマは版 2 とし、版 1（版なしを含む）は完了済みに移行する。
端末状態がなくても既存の設定ファイルがある場合は完了済みとする。版 2 の明示的な未完了状態は再表示する。

## 9. 操作体系（R5）

### 9.1 ホットキー（既定案。すべて変更できる）

| 操作 | 既定キー |
|---|---|
| ランチャーを開く | Ctrl+Alt+Space |
| 左／右／上／下の半分 | Ctrl+Alt+←/→/↑/↓ |
| 四分割（左上・右上・左下・右下） | Ctrl+Alt+U / I / J / K |
| 1区画ずつ拡大・縮小 | Ctrl+Alt+Shift+矢印 |
| 区画単位で移動 | Ctrl+Alt+Win+矢印 |
| 左／右／上／下の隣へ寄せる | Ctrl+Alt+Shift+J / L / I / K |
| 現在のモニターを整列 | Ctrl+Alt+A |
| 横一列／縦一列／メインとスタックで整列 | Ctrl+Alt+Shift+H / V / M |
| 全モニターを整列 | Ctrl+Alt+Shift+A |
| 隣のモニターへ投げる | Ctrl+Alt+PageUp / PageDown |
| 一時的に無効化 | Ctrl+Alt+Pause |

標準スナップを止めている間は、Win+矢印キーにも同じ操作を割り当てられる（§8）。ホットキーが競合した場合は、設定GUIで競合を検出して表示する。

### 9.2 ランチャー

- 対象ウィンドウがあるモニターの上に、半透明のオーバーレイとしてグリッドを表示する。
- **範囲選択:** マウスで区画をドラッグするか、キーボードで始点と終点の区画を指定して、ウィンドウの位置とサイズを決める（Divvyのような操作）。
- **プリセット:** よく使う配置（半分、1/3、整列など）をボタンで並べる。
- **フリック:** ランチャー上でウィンドウのサムネイルを投げると、§5 の物理モデルで配置される。
- Esc またはランチャー外のクリックで閉じる。

### 9.3 タイトルバーの長押し

```
WH_MOUSE_LL で左ボタンの押下を検知
  → WindowFromPoint → GetAncestor(GA_ROOT) で対象ウィンドウを特定
  → SendMessageTimeout(WM_NCHITTEST) が HTCAPTION を返すか確認
  → 長押しタイマーを開始（既定 450ms、変更可）
     ├─ 時間内に指定距離（既定 6px）以上動いた → キャンセル（通常のドラッグ、§5.2 のスナップへ）
     └─ 時間内に動かなかった → 標準の移動ループを取り消し、カーソル位置にランチャーを開く
```

- Chrome や Electron など独自のタイトルバーを持つアプリも、多くは `WM_NCHITTEST` に HTCAPTION を返すので判定できる。判定できないアプリ向けに、ウィンドウ上端 32 論理 px を長押し対象とする補助ルールを使う。
- **上端の補助ルール（`Snapwell.Core.Input.TopBandRule`）:** まず既存の `isCaption(handle, position)` を確認し、false の場合だけ補助判定を使う。押下位置が `WindowSnapshot.VisualBounds` の左端以上・右端未満、上端以上・上端から 32 論理 px 未満ならタイトルバーとみなす。高さは `monitor.Scale` で物理 px に換算し、倍率が 0 以下または有限でない場合は 1 とする。`VisualBounds.Contains(monitor.WorkArea)` の場合は補助対象から除く。モニター全体の領域ではなく作業領域を覆うかで判定するため、全画面に加えて最大化したウィンドウも除外する（誤作動を避けるための推測。実機未確認）。矩形がモニターをまたぐ場合も、既存の `CommandPlanner.SelectMonitor` が選んだモニターの作業領域と倍率を使う。押下時の `Handle` 内で矩形比較を済ませ、`LongPressCandidate.InTopBand` に保存する。タイマー発火時はヒットテストと保存済みの補助判定のいずれかが通り、現在のカーソルも従来の許容半径内にある場合だけ開く。
- 移動ループの取り消し方法（`ReleaseCapture` や Esc キーの送信など）はアプリごとに挙動が違う可能性があるため、要検証。
- **いまの実装（`Snapwell.App.Dragging.LongPressDetector`）:** 移動ループは取り消さない。左ボタンの押下から 450 ms、押した位置から 6 論理 px（モニターの拡大率で換算）以内なら、タイマーの発火時に `SendMessageTimeout(WM_NCHITTEST, SMTO_ABORTIFHUNG, 100 ms)` で HTCAPTION を確かめ、そのウィンドウを対象にランチャーを開く。ヒットテストは低レベルフックのコールバックの外、常駐のロックの外で行う。ボタンを押したままなので移動ループは続くが、動かさずに離せばウィンドウは動かず、離したあとにランチャーを操作する。開いたあと同じ押下で 6 論理 px を超えて動かすと、ランチャーを閉じて通常のドラッグに戻す（そのドラッグでは吸着しない）。判定時間（既定 450 ms、150〜2000）と距離（既定 6 論理 px、2〜32）は設定画面の「全般」で変えられ、押下の時点で読む。設定の再読み込みは常駐部分ごと作り直すため、押下中に保存すると、その押下の長押しは取り消される（ほかの設定と同じ扱い。次の押下から新しい値になる）。補助ルールは上記の上端 32 論理 px の判定を使う。

## 10. 対象ウィンドウの扱い（R11）

### 10.1 分類

| 分類 | 判定 | 位置の変更 | サイズの変更 |
|---|---|---|---|
| 通常のウィンドウ | 表示中、トップレベル、`WS_THICKFRAME` あり | ○ | ○ |
| サイズ固定のウィンドウ | `WS_THICKFRAME` なし、または最小＝最大サイズ | ○ | ×（区画内に中央寄せ、または投げた方向の角に寄せる） |
| ポップアップ・フライアウト（例: Claudeのタスクバーから開く小型チャット） | `WS_POPUP`、ツールウィンドウ、最前面など | ○ | × |
| UWP アプリ | `ApplicationFrameWindow` | ○（フレームウィンドウを移動する） | ○ |
| 管理者権限のウィンドウ | 本体より高い整合性レベル | 本体を管理者として起動したときだけ○ | 同左 |
| 除外 | デスクトップ、タスクバー、スタートメニューなどのシェル、クローキング中のウィンドウ、全画面の排他モード | × | × |

- フライアウトはフォーカスを失うと閉じるものが多いため、フォーカスを奪わずに（`SWP_NOACTIVATE`）移動する。ホットキー操作時は直前の前面ウィンドウを対象にする。
- アプリごとの除外ルールや強制ルール（プロセス名、ウィンドウクラス、タイトルの正規表現で指定）を設定できるようにする。
- 管理者権限のウィンドウ: UIPI（User Interface Privilege Isolation）により、通常権限からは操作できない。オプションで、タスクスケジューラ経由で管理者として自動起動できるようにする（§11）。

### 10.2 最小・最大サイズの扱い

他プロセスの `WM_GETMINMAXINFO` の値は直接取得できない。そのため、サイズを適用したあとに実際の矩形を読み直し、区画とずれていれば位置を補正する。

### 10.3 モニター構成の変化への対応

- モニター構成（各モニターのID、解像度、配置）の識別子をキーとして、ウィンドウの配置を保存する。
- `WM_DISPLAYCHANGE`、スリープ復帰（`WM_POWERBROADCAST`）、ドック着脱を検知したら、構成が落ち着くのを待ってから（デバウンス）、該当する構成の配置を復元する。
- 競合製品 komorebi で未解決になっている不具合（スリープ復帰やドック着脱で状態が失われる）を、本製品の重点テスト項目にする。

| 方式 | 用途 |
|---|---|
| MSIX の `StartupTask` | ストア版・MSIX版の標準 |
| `HKCU\...\Run` | ポータブル版 |

設定GUIで「自動起動する」「管理者として起動する」を切り替える。
ポータブル版の自動起動は設定画面の「全般」で切り替える。状態はレジストリだけが正で、同期で他の PC に広がるため設定ファイルには入れない。

**OS 設定の復元との関係:** §3.2 の原則 4（OS 設定を変えたら元に戻す）の例外として、自動起動の登録は終了しても消さない。登録と削除は利用者が設定GUIで切り替えたときだけ行う。開発中のビルドでの登録は試験のためだけで、試験が終わったら削除する（CLAUDE.md の「守ること」）。

## 12. 設定（R8・R9）

### 12.1 保存形式

- JSON（スキーマのバージョンを持たせ、古い形式から自動で移行する）。保存先は `%APPDATA%\Snapwell\settings.json`。
- **ポータブル設定**（ホットキー、分割案、間隔、操作感、アプリごとのルール）と、**端末固有の状態**（モニター構成ごとの配置、標準スナップの退避値）を別ファイルに分ける。同期とエクスポートの対象はポータブル設定だけにする。
- スキーマの版 2 で OpenLauncher の既定のキーを移行した。本体は settings.json を監視して取り込む（書くのは設定画面だけ）。
- 現在のポータブル設定のスキーマは **版 6**。版 5 以下の既存値を保ち、追加項目は既定値で補う。版 7 以上は読み取り専用で保護し、保存・書き出しで上書きしない。
- 見た目の設定は `CornerPreference`（Windows の既定／角丸を強制する／小さい角丸／角丸なし。既定は変更しない）、`ShowZoneLines`（区画の線、既定オン）、`ShowPredictionLine`（投げた先への予測線、既定オン）。大きな角丸は引き続き準備中・要検証。
- グリッドの設定は共通の `Grid`・`Gap`・`Edge` に加え、`MonitorGrids`（識別子 → 列数・行数・任意の間隔と余白。既定は空）を持つ。識別子は現在の `MonitorInfo.DeviceName`。大文字小文字を区別せず、未設定のモニターでは共通値を使う。表示番号が変わる接続変更は設定を選び直す必要がある。間隔と余白の未指定は共通値を使う。
- `SnapAfterResize`（既定オフ）は、手動リサイズの終了時に、中心のあるモニターの最寄りの区画境界へ揃える。最大化・最小化・サイズ固定・自プロセス・移動だけの操作は除外し、最小サイズを満たす区画範囲がない場合は移動しない。
- 角の変更前の値と対象プロセスの識別は `%LOCALAPPDATA%\Snapwell\corners.json` に退避する。既定へ戻すとき、無効化、終了、次の起動で復元し、復元に失敗した記録は残す。他プロセスに対する見た目の効果は実機未確認。

### 12.2 インポート・エクスポート

- 設定GUIからファイルに書き出し、読み込む。読み込み時には差分を表示し、全体を置き換えるか一部だけ取り込むかを選べるようにする。

### 12.3 クラウド同期（段階的に導入）

| 段階 | 方式 |
|---|---|
| 1 | ユーザーが選んだ同期フォルダー（OneDrive、Dropboxなど）に設定ファイルを置き、ファイルの変更を監視して取り込む。サーバーは不要 |
| 2 | アカウントを使った同期（GitHub Gist など）。必要性を見て判断する |

競合した場合は更新時刻で判断し、取り込む前に必ずバックアップを残す。

## 13. 角丸（R10）

| 方式 | 内容 | 評価 |
|---|---|---|
| DWM の角設定 | `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` で角丸、小さい角丸、角丸なしを指定する | Windows 11標準の仕組みで、影も保たれる。ただし**半径は固定**（約8px）。他プロセスのウィンドウに適用できるかは要検証 |
| ウィンドウ領域 | `SetWindowRgn` で角を切り取る | 半径は自由に決められるが、ギザギザになり、DWMの影が消える。アプリと干渉しやすいので非推奨 |
| オーバーレイで覆う | 角の部分を背景で覆うマスクを重ねる | 半径は自由だが、背景と合わせ続けるのが難しい |

**方針:** まずDWMの角設定を「角丸を強制する」機能として実装する（Windows 11の既定で角丸にならないウィンドウにも適用する）。macOS相当の大きな半径は、技術検証の結果を見て判断する。

## 14. 非機能要件

| 項目 | 目標 |
|---|---|
| 応答性 | ホットキーを押してから配置が終わるまで50ms以下（アニメーションなしの場合） |
| アニメーション | ディスプレイのリフレッシュレートに同期する（`DwmFlush` などで待つ）。演算は240Hzの固定ステップ |
| 常駐時の負荷 | アイドル時のCPU使用率ほぼ0%（フレームループは静止時に停止する）。メモリ50MB以下 |
| 堅牢性 | フックの処理が遅いとOSにフックを外されるため、フックのコールバックは即座に戻り、処理は別スレッドに渡す |
| 安全性 | OS設定を必ず復元できる（§8）。クラッシュ後の自動復旧 |
| 多言語 | 日本語・英語 |
| ライセンス | feel（MIT）のアルゴリズムを移植する場合は著作権表示を同梱する。本製品のライセンスは別途決定する（業務利用を明確に許可する方針） |

## 16. モックアップ作成の対象画面

次の工程で作るモックアップは以下を想定する。

1. **ランチャー**（グリッドのオーバーレイ、範囲選択、プリセット、ウィンドウのサムネイル）
2. **スナップ中の表示**（投げたウィンドウの軌跡、予測される停止先の区画のハイライト）
3. **設定GUI**（一般、分割と間隔、ホットキー、操作感（feel のプリセットとパラメーター）、アプリごとのルール、標準機能の制御、同期とインポート・エクスポート、外観（角丸））
4. **トレイメニュー**（有効・無効、プロファイルの切り替え、設定を開く）
5. **初回セットアップのウィザード**（標準スナップの停止への同意、ホットキーの確認、分割案の選択）
